## Execution order

**Phases 1–4 are shipped and the app is in real daily use, which changes what matters next.** The brief's numbering above still describes the _scope_ of each phase, but the running order below supersedes it. Reprioritized 2026-07-30, agreed with Geoffrey.

### 1. Compile / Export ✅

Assemble binder items into a finished manuscript — the app can now get prose back out. **File → Compile Manuscript… (⇧⌘E).** Shipped in PR #8.

- **Selection**: a checkbox tree over the binder; ticking a folder takes everything beneath it, and folders show a partial state. Binder order is the output order. Trash is excluded _by construction_ — `trash` is a separate tree that the compiler never walks, and a test passes a trashed id in explicitly to prove it cannot leak.
- **Formats**: plain text, Markdown, and `.docx`. The `.docx` writer is dependency-free (`lib/docx.ts` builds the OOXML and its own stored-entry ZIP), so no new packages entered the tree.
- **Scene separators**: `#`, `* * *`, blank line, or a custom string; a page break replaces the separator at folder boundaries in `.docx`.
- **Front matter**: optional title page with the project title and the compiled word count.
- **Formatting**: bold/italic/highlight map to each format — Markdown re-uses the editor's own serializer, so compiled Markdown is byte-identical to the stored files (tested against real fixtures). Plain text keeps the words and drops the markup, since inventing asterisks would just be Markdown again.
- **Safety**: a checkpoint is committed before compiling, and the documents are re-read afterwards, so the exported manuscript is always a state that can be returned to.
- The dialog shows a live preview plus word and document counts, comparable with the status bar.

Deferred: EPUB and PDF (the hard formats — the block model in `shared/types.ts` is format-independent, so each is a new serializer rather than new plumbing).

### 2. Local backup remote (cheap half of F-01) ✅

Off-machine redundancy with no account, no OAuth and no network. **Project → Backup…** mirrors a project into a second repository on disk (external drive, synced folder, network share) and restores from one. Shipped in PR #10.

**The premise in the original plan was wrong, and it matters for Phase 5.** "A git remote can be a filesystem path" is true of real git but **not of isomorphic-git**, which has no local transport at all — `push` requires an HTTP client, and both `file:///path` and a bare path fail with `MissingParameterError`. Shelling out to system git would break the brief's §10 decision to require no git install. So the mirror is done the way git's own "dumb" transport does it: copy objects, then move refs. See `main/wyrm/backup.ts`, which documents the three invariants that make that safe:

1. **Objects are copied before refs move.** Interrupted halfway, the backup holds unreferenced objects (harmless garbage) and its refs still describe a complete, older history. The reverse order leaves a ref pointing at a missing object — a corrupt repository.
2. **Every object is staged and renamed into place.** A torn write sitting at its final name would be treated as "already present" by every later backup, making the corruption permanent and silent.
3. **Fast-forward only, and nothing is ever deleted.** If the backup holds commits this project does not, the backup is left untouched and the writer is told. There is deliberately no force option.

Also shipped: the backup carries variant branches, not just the main line; restore always creates a **new** project folder so it cannot overwrite an open one; auto-backup after each checkpoint is opt-in and can never block or fail a commit; and a successful backup is verified by reading every file of the manuscript back **out** of the backup, so "backed up" means "provably recoverable" rather than "the copy returned no error".

### 3. Phase 5 — GitHub sync (+ the rest of F-01) ✅

Shipped in PR #11: OAuth device flow, auto-sync after each checkpoint, offline queueing, the merge-conflict resolution screen on the existing diff viewer, and local-only as an explicit first-class choice. **Project → Sync Settings… / Sync Now.**

Design decisions that will matter later, recorded in `main/wyrm/sync.ts`'s header:

- **The working tree is the single source of truth for every sync commit.** isomorphic-git's `merge` never touches the working directory (verified by experiment) — trusting its ref move would let the next autosave commit the stale tree back over the merge, silently undoing the other device's work. So `merge` is only ever a conflict _detector_ and a content _oracle_ (`noUpdateBranch` both times); the final state is always materialized to disk first and committed from there with explicit parents.
- **Prose never auto-merges.** diff3 would happily interleave paragraphs of fiction edited on two devices; in a prose tool that is not a feature. Frontmatter merges structurally (newer `modified` wins, per-field three-way — so timestamp noise never nags), but two devices editing the same document's _text_ always goes to the writer: keep mine / take theirs / keep both, with "both" shelving the other device's version as a variant pointing at the remote commit itself.
- **A binder conflict cannot orphan a document.** After every merge, any `documents/*.md` not reachable from binder or trash is re-attached to the binder root as "(recovered)" — resolving project.json either way is safe.
- **The sacred page holds for sync.** A background sync that finds conflicts raises a quiet status-bar flag; only a sync the writer asked for may open the resolution screen.
- Auth: device flow (no client secret; the one-time OAuth app client id is entered in Sync Settings), token encrypted via the OS keychain (`safeStorage`) at rest, remote URL in `.git/config` — none of it ever inside the synced content.

Deferred from this pass: syncing to a remote whose default branch isn't `main`; structural (rather than mine/theirs) binder merge; multi-account.

### 4. Quality-of-life batch — 🔨 in progress

Split in two, because "appearance you can live in" and "navigation you can drive" are unrelated changes that would otherwise land as one unreviewable diff.

**4a. Reading comfort ✅** — F-05's comfort variants and F-06, shipped in PR #12. Appearance is now persisted app-level (`settings.json`), so a chosen palette survives a restart — previously it was React state and reset on every launch, which made the phosphor themes decorative rather than usable.

- The theme axis was `data-terminal`, which only ever _looked_ writing-pane-scoped — it has always remapped the root `--ink`/`--paper` pair for the whole app. Renamed to **`data-palette`** to stop the name lying, and split "palette" from "CRT effects": glow and scanlines now belong only to `green`/`amber`, so a comfort variant can be two-colour without pretending to be a monitor.
- New palettes: `ereader` (warm grey / deep blue), `night` (tan / brown), `dark` (inverse — deliberately `#e6e6e6` on `#0d0d0d`, since full-contrast white on black blooms over a long session).
- **Every palette must restate all five SVG data-URIs** (3 dithers, 2 scrollbar arrows) — the ink colour is baked into each one, so a palette that forgets them keeps the previous theme's patterns and looks subtly broken. This is the single easiest way to add a broken theme.
- F-06 geometry (`--measure` in `ch`, `--prose-size`, `--prose-leading`) rides as inline custom properties on the root, so the page reflows live. The measure is in `ch` on purpose: the column stays the same number of characters wide at any text size, which is what actually governs readability.
- Dialogs became a flex column with a scrolling body and a `92vh` cap — the enlarged Preferences pushed its own title bar and Close button off-screen, and losing the way out of a dialog is worse than a scrollbar.

**4b. Navigation ✅** — F-07, full-project search and the ⌘K palette, shipped in PR #13. **⌘K** jumps to any document, story-bible entry or command; **⇧⌘F** searches inside the prose; **F10** or **⌥F** enters the menu bar.

- F-07 follows the WAI-ARIA menubar pattern rather than an invented one (roving tabindex, ←/→ between menus with or without one open, ↑/↓ within, Home/End, type-ahead, Esc), which also makes the bar screen-reader navigable. Dialogs get a real focus trap — without one, Tab walks out of a modal into the manuscript behind it, so a keyboard-only writer can type into a document they cannot see. The binder gets ↑/↓/←/→, Enter, F2, ⌫, with the **keyboard cursor kept distinct from the open document**: arrowing browses, Enter opens. Showing them identically would claim a document had been opened when it had not.
- `lib/search.ts` backs both surfaces so "what is findable" is decided once. Search is plain case-insensitive substring (fuzzy matching inside 100,000 words returns noise); the palette is fuzzy subsequence with a bias toward word starts. Trash is excluded from both, as in compile.
- **Search runs against the plain-text projection, not the stored Markdown.** Bodies carry `**` and `==` mid-sentence, so searching the raw text silently fails for any phrase spanning a bold word — "Not louder. Exactly" never matches `Not louder. **Exactly**` — and snippets show storage syntax instead of prose. Parsed results are cached by body string, since bodies do not change while a query is being typed.

**4c. Writing stats ✅** — daily count, goal and streak, shipped in PR #22. **Project → Writing Stats…**, plus a today-vs-goal indicator in the status bar.

It needed a data model, as predicted — but not a new one. **The stats are derived from git history rather than recorded anywhere.** Every checkpoint is already a timestamped snapshot of the whole manuscript, so "how many words existed on Tuesday" is a question the repository can already answer. That choice fell out of Geoffrey's decision that stats should follow the project across devices, and it beat a tracked `stats.json` on every axis that mattered:

- **No commit churn.** A tracked stats file would dirty the working tree every time the counter moved, turning a quiet session into a stream of commits about nothing.
- **No merge conflicts.** Two machines writing on the same day would both edit that day's row; instead they contribute commits, and merging commits is what git is for.
- **It syncs for free**, because history syncs — which is what was actually asked for.
- **It works retroactively.** Geoffrey's real project reported its whole back-history the first time the feature ran, rather than starting from zero on ship day.

Cost is a walk over history, kept cheap in `main/wyrm/stats.ts` by memoising word counts against blob oids: an oid is a content hash, so an unchanged document is counted once no matter how many commits span it, and the work scales with distinct document versions rather than commits × documents.

Decisions worth keeping straight:

- **Three counting modes, the writer's choice** (Preferences → WRITING STATS). Net, added-only, and net-floored-at-zero disagree most on exactly the day that matters — one spent cutting — so Geoffrey asked for the choice rather than a house opinion. `net` is the default and shows a cutting day as the loss it was.
- **The streak counts showing up, not hitting the goal.** A day spent cutting three thousand words of flab keeps it. A streak that punished revision would quietly discourage revising, which is the opposite of what a drafting tool should do. An unfinished day is also not a broken streak — nothing written yet today still reads from yesterday.
- **Reading the stats checkpoints first**, the same way compile does. History is the only source of these numbers, so uncommitted work would otherwise be invisible and a writer who just wrote 300 words would be told they wrote none.
- `countWords` moved to `src/shared/words.ts`. The status bar counts in the renderer and the engine counts in main, main never imports from renderer, and two copies would drift into quoting different numbers for the same text.
- **The ambient counters can be switched off entirely** (Preferences → WRITING STATS → "Show word counts while writing"), requested immediately after the first pass. One switch takes the editor header count, the status-bar count and the today indicator together — leaving any one behind would defeat the point. Writing Stats still reports everything on demand: choosing not to be watched while drafting is a different thing from not wanting to know.

**Found while building:** git commit timestamps are whole **seconds**, so checkpoints made in the same second compare equal, and a stable sort left them in `git.log`'s newest-first order — the day's _oldest_ commit then defined where the day ended, reporting a full day of writing as a total of zero while `net`/`added` stayed correct, which is what disguised it as a plumbing failure. Ties now break on reversed log order. Not a test artifact: an autosave landing in the same second as a manual checkpoint hits it, as does project creation followed by a first save.

Deferred: a live in-session counter (the status bar's per-document count already covers "am I writing"), and best-day/total-words-this-month style figures.

### 5. Story-structure cluster (F-10 first, then F-02, F-03, F-04, F-11, F-12, F-13) ✅

Timeline, plot graph, plotline tracking, graph views, the world map and nested locations — **every item in this cluster is now shipped.** F-10 (pins & tags) gated everything else and was built first; F-02/F-29 (timeline), F-03 (plot graph), F-04 (plotline tracking) and F-11 (character graph) followed as the primary sequence the brief laid out, each a view over F-10's tag/pin data or a lightweight record following the same storage pattern (`Plotline`, `Relationship`, and now `MapPin`). F-13 (nested locations) was picked up deliberately as the prerequisite F-12 (world map) needed — a `parentId` field lets World Book entries nest — and F-12 closed the cluster the same day, placing locations on a map with the same one-record-per-placement pattern that answered its own long-standing storage question along the way.

**5a. Pins, tags & factions (F-10) ✅** — shipped. `DocMeta` and `Entity` both gain `tags?: string[]`; `DocMeta` gains `pins?: string[]` from `DOC_PINS`, `Entity` gains `pins?: string[]` from `CHARACTER_PINS` (`src/shared/types.ts`). Both are plain frontmatter, matching how the story bible already stores everything — no `project.json` index, so the model versions and diffs with the file it describes.

- **Tags** are free-form, added by typing into the "+ tag" field and pressing Enter; a faction ("House Voss") is nothing but a tag several entities share, and `scene` (`SCENE_TAG`) is nothing but a tag on a document — no new `BinderNodeType`, so F-02/F-03/F-04 can filter on it later without any document-kind change. **The Scene tag gets its own checkbox in the doc header, not a typed tag** — found unintuitive in testing ("is this a scene?" is a yes/no question, not a word to remember and spell correctly). The data model is unchanged: the checkbox reads and writes `SCENE_TAG` in the same `tags` array, it's just hidden from the ordinary tag-chip list so it isn't shown twice. Every other tag, including factions, stays free-typed.
- **Pins** are a closed, app-shipped vocabulary and cannot be invented by the writer — a dropdown toggles membership. Documents get `DOC_PINS` (Setup, Rising Action, Climax, Falling Action, Resolution); characters get `CHARACTER_PINS` (Protagonist, Antagonist, Viewpoint Character). World/glossary entities have no pin vocabulary yet, per the original design — none invented speculatively.
- **UI split by component's own convention rather than one shared widget**: the writing terminal's tags/pins bar (`Editor.tsx`'s `DocMetaBar`) writes immediately, the same "no debounce for metadata" reasoning as 4c's stats; the story-bible entry editor (`EntityEditor.tsx`) queues tags/pins in local state like every other field there, applied on the existing explicit **Save Entry**. Both bars live in chrome, not on the page itself — the doc header row is a second flex row inside `.terminal-chrome`, which only appears on hover alongside the title/word-count row already there (the page-is-sacred house rule extends to metadata, not just notifications).
- `entities.ts`'s `writeEntity` omits `tags`/`pins` from frontmatter entirely when empty, so entities untouched by F-10 keep the frontmatter they always had rather than gaining `tags: []` on every save; `gray-matter`'s YAML dumper throws on an explicit `undefined` value, which is why the store's `updateDocMeta` deletes the key rather than setting it to `undefined` when a writer removes the last tag.

Deferred, as scoped at design time: the skeuomorphic treatment (pin heads, luggage-tag-shaped tags, still 1-bit) — the current chips/toggles are functional but plain, matching the rest of the chrome rather than the request's original visual ambition. Revisit alongside F-20/F-21/F-22's other editor-pane visual work rather than blocking F-02/F-03/F-04 on it.

**5b. Timeline (F-02) ✅** — shipped. **Project → Timeline…** (also in the ⌘K palette) lists every `scene`-tagged document as a card, ordered by the new `DocMeta.timelineOrder` with binder order as the fallback for a scene that has never been dragged; an optional `DocMeta.timelineDate` free-text label rides alongside but never affects sort order (`shared/types.ts`).

- **No standalone card entity and no `project.json` index** — a card is nothing but a scene-tagged document, matching F-10's storage philosophy exactly. `lib/timeline.ts`'s `timelineCards` is a pure read-through: filter by `SCENE_TAG`, sort by `timelineOrder ?? <binder position>`.
- **Reordering never rewrites the rest of the list.** `orderBetween` assigns the dropped card a fractional rank — the midpoint of its new neighbours' `timelineOrder` values (or ±1 past an end) — so moving one card is one `writeDoc` call, not a renumbering pass across every scene.
- **The store acts on an arbitrary doc id, not just the active document.** `setTimelineOrder`/`setTimelineDate` read whichever document is targeted (falling back to `api.readDoc` when it isn't the one open in the editor), since the card a writer drags on the timeline is rarely the document currently open for writing — unlike F-10's `updateDocMeta`, which only ever touches the active doc.
- The dialog fetches its own doc list via `api.readAllDocs` on open (same pattern as the entity editor's backlinks) rather than keeping a live store slice — the timeline is opened rarely enough that a fresh read on open is simpler than keeping another piece of global state in sync.

Deferred, as scoped at design time: a real calendar/duration system (explicitly the heavier of the two dated-events options, not chosen); per-thread or per-POV timelines (one timeline per project was chosen). The plain-row visual was superseded almost immediately — see 5c.

**5c. Timeline: line-graphic view (F-29) ✅** — shipped the same day it was requested. **Project → Timeline… → Line** (a tab next to **List**, which stays — see below) redraws the same cards as markers on a literal line rather than rows. Design settled 2026-08-01 with Geoffrey:

- **Position is a literal coordinate, reusing `timelineOrder` as-is** — no new field. The list view already treated it as a sortable rank; the line view is the same number read as an x-position, so nothing added to `DocMeta`.
- **An in-world date still never affects placement** — consistent with 5b's original decision, not reopened.
- **A stack is a visual coincidence, not stored data** — two cards land on a stack by sharing a grid position; nothing records "these happen at once" beyond that. `lib/timeline.ts`'s `stackByPosition` groups cards for rendering only.
- **Dragging snaps to a grid (`TIMELINE_GRID`) instead of pixel-precise placement.** The grid size is exactly 1 — larger than it first sounds, and load-bearing: `TimelineLineView`'s `PX_PER_UNIT` (140) is sized so one grid step never renders narrower than a card (108px). A finer grid was tried first and found broken in the browser preview, not just in theory — a drop landing close to but not exactly on another card rendered as an unreadable partial overlap, neither a clean gap nor a clean stack. The invariant (`PX_PER_UNIT * TIMELINE_GRID >= card width`) is written down at both ends (`lib/timeline.ts` and `TimelineLineView.tsx`) and has a regression test (`timeline-line-view.test.tsx`) asserting no two different grid positions ever render closer than a card width apart.
- **List and Line are both kept, as a tab toggle**, rather than Line replacing List outright — the request said "I should be able to view the timeline as" a line, which reads as adding a view rather than retiring the one already shipped and tested.
- **Click vs. drag is decided entirely from the pointer-event sequence** (movement past a small pixel threshold means drag, not click) since there's no separate drag handle — resolved via a ref read synchronously in `onPointerUp` rather than a subsequent `onClick`, because by the time a browser's own `click` event fires, the drag state has already been cleared and reading it there would silently misfire on every click that followed a drag.

Deferred, as scoped at design time: a real calendar/duration system, per-thread timelines (both same as 5b, unchanged); keyboard-driven reordering (Enter still opens a card via keyboard; only mouse can reposition one, matching the list view's own drag having no keyboard equivalent either).

**5d. Plot graph (F-03) ✅** — shipped. **Project → Plot Graph…** plots the same scene-tagged, timeline-ordered cards as 5b/5c, with tension on the y-axis instead of chronology — a curve reading the dramatic shape of the manuscript at a glance. Design settled 2026-08-01:

- **Tension is manual only, set by dragging a node vertically** — 0–10, no scoring model, nothing derived. `DocMeta.tension` is a new optional field; unset scenes render at the midpoint (5) so they show up on the curve without implying "no tension yet" at either extreme, but nothing is written to disk until a writer actually drags a node.
- **The x-axis reuses `timelineOrder` as-is**, the same coordinate F-02/F-29 already read — the plot graph is a third view over the same one axis rather than a second "narrative order" concept. `lib/timeline.ts`'s `timelineCards` (already shared by both timeline views) is reused unchanged; `TimelineCard` just grew an optional `tension` field to carry it through.
- **One curve, not one per plotline** — the original sketch asked about overlaying curves per plotline, but that needs F-04's plotline model to exist first, and it doesn't yet. Building for multiple curves now would mean designing two undesigned features at once; single-curve ships today and multi-curve is a natural extension once F-04 gives it something real to key off.
- **Drag mechanics mirror F-29's line view deliberately**: click vs. drag decided from the pointer-event sequence (a movement threshold, not a separate handle), resolved via a ref read in `onPointerUp` for the same race-avoidance reason documented in 5c. The one difference is the value dragged live-previews unclamped and unrounded (so the curve moves smoothly under the pointer) and only gets `clampTension`'s round-to-whole-number-in-range treatment on release — there's no grid-overlap hazard here since nodes don't collide horizontally the way timeline cards can.

Deferred, as scoped at design time: keyboard-driven tension adjustment (Enter opens a card same as the other two views; only mouse sets tension); a real "what does tension mean" rubric — it's explicitly whatever the writer says it is.

**5e. Plotline tracking (F-04) ✅** — shipped. **Project → Plotlines…** tracks main plot, B-plots, romance arcs, and any other thread the writer names, answering "which threads are still open?" and "which scenes advance this arc?" Design settled 2026-08-01:

- **A plotline is its own lightweight record** (`Plotline`: name, colour, status) — deliberately neither a story-bible `Entity` (a plotline never auto-links in prose, which is what `Entity` exists for) nor just a tag (a tag has nowhere to hang a colour or a status). Stored the same way as entities — one frontmatter-only file per plotline, in a new `plotlines/` directory (`main/wyrm/plotlines.ts`, mirroring `entities.ts`'s shape exactly) — so it versions and diffs with the project the same way everything else does.
- **A scene joins a plotline by tag, matching its name** — not a stored id. Typing a plotline's name into a scene's existing "+ tag" field (F-10) is the entire linking mechanism; no new UI on the document side at all. Renaming a plotline is consequently a visible, deliberate act (re-tag the scenes that should follow), never a silent id remap.
- **Status is a manual toggle on the plotline itself** (open/resolved) — not derived from any scene's pins. Consistent with `DocStatus` (draft/revised/final) already being a plain manual field rather than inferred from anything.
- **Setup/payoff beats reuse F-10's existing `DOC_PINS`** (`Setup` / `Resolution`) rather than a plotline-specific vocabulary — a scene tagged with a plotline's name _and_ pinned `Setup` (or `Resolution`) is read as that plotline's setup (or payoff) beat. One shared vocabulary, no new pin concept to design or maintain.
- **Colour is a closed set of six swatches** (`PLOTLINE_COLOURS`), not a free color picker — same reasoning as `DOC_PINS`/`CHARACTER_PINS` being closed vocabularies: two plotlines are always visually distinguishable without depending on a writer's color sense, and the swatch list stays finite. Colour is scoped to the Plotlines dialog only, per the design decision — it does not propagate to the binder, timeline, or plot graph (a larger, cross-cutting change explicitly deferred).
- **One curve on the plot graph remains unchanged for now** — F-04 existing is what F-03 was waiting on to make multi-curve overlays possible, but the plot graph itself wasn't touched in this pass; that's a follow-up, not part of what shipped here.

Deferred, as scoped at design time: colour propagating beyond the Plotlines dialog; multi-curve overlays on the F-03 plot graph (now unblocked, not yet built); any automatic "is this plotline actually resolved" inference.

**5f. Character graph (F-11) ✅** — shipped, completing the story-structure cluster's primary sequence (F-10 → F-02/F-29 → F-03 → F-04 → F-11). **Project → Character Graph…** maps characters into faction clusters with typed, directional relationship edges between them. Design settled 2026-08-01:

- **Relationships are typed and directional** — a `Relationship` record (`fromId`, `toId`, `label`) rather than a symmetric, unlabelled edge. "Sibling of" reads the same both ways but "estranged from" doesn't, and only a directional edge can answer the question the original request actually asked ("who is estranged from whom").
- **A new lightweight record, the same shape of decision as F-04's `Plotline`** — not a field on the character `Entity` (a `relationships: []` list on each character would drift out of sync the moment one side of a two-way relationship was edited without the other) and not its own story-bible entity (it never auto-links). Stored identically to plotlines: one frontmatter-only file per relationship, in a new `relationships/` directory (`main/wyrm/relationships.ts`, mirroring `plotlines.ts` exactly).
- **Faction clustering reads a character's first tag** — F-10 deliberately never added a dedicated "faction" field (a faction is just a tag on `Entity`), so there is no marked field to group by. `lib/characterGraph.ts`'s `clusterCharacters` takes the first tag as the cluster key; untagged characters land in a single "Ungrouped" column rather than being hidden. This is a reading of existing data, not a new concept — a character with several tags doesn't get a second, more "correct" grouping key defined anywhere.
- **Layout is deterministic, not manually draggable** — columns per cluster (alphabetical, Ungrouped always last), nodes stacked vertically within one. No node-position storage, no drag-to-reposition; this matches the design pass's scope (edge type, storage model, and graph scope were the three questions settled — manual layout was never one of them).
- Clicking a node opens the character's full entry (`showEntity`), same as clicking a name anywhere else in the app; the graph's own inline form (two selects plus a label field) is the only way to add a relationship, with a matching list below for editing/deleting one without needing to trace a line on screen.

Deferred, as scoped at design time: manual node dragging/positioning; relationships between non-character entities (world/glossary) — the request was specifically about characters; propagating faction colour the way F-04 keeps plotline colour scoped to its own dialog.

**5g. Nested locations (F-13) ✅** — shipped. World Book entries can now nest (a building inside a neighbourhood inside a city inside a country), settled and built 2026-08-01 as a prerequisite the writer chose to design before picking up F-12 (world map), which depends on it. Design decisions:

- **A single `parentId` field on `Entity`, meaningful only for `world` entities** — no separate hierarchy structure, no second file to keep in sync. The tree is never materialized; `lib/locations.ts`'s `locationChain` walks parent pointers on demand each time a breadcrumb is needed. Same "no second source of truth" reasoning as every other F-nn this session (tags, pins, plotlines, relationships).
- **Set via a "Parent Location" dropdown in the full entity editor**, not a visual nested tree in the World Book binder section — the binder list stays flat for now. Mechanism first, matching F-12's own planned first pass (placeable pins before map decoration) and F-04/F-11's dialogs (a form field before a fancier direct-manipulation UI).
- **Cycles are prevented at write time, not just walked around at read time.** `wouldCreateCycle` filters the dropdown's own option list — a location can never be offered as its own ancestor's parent — so a cycle can't be created through the UI at all. `locationChain` still guards against one anyway (a `seen` set that stops rather than loops forever), because hand-edited frontmatter could introduce one outside the app's control, and a graph-walk that can hang on bad data is worse than one that returns a partial, honest answer.
- **Nesting surfaces as a read-only "located in" breadcrumb**, in both the full editor (live preview of the dropdown's current choice, before Save Entry commits it) and the side reference panel — not as a change to auto-linking. Mentioning "Harrowgate" in prose still links only Harrowgate; the breadcrumb is discoverable by opening the entry, not injected into the manuscript's link behaviour.

Deferred, as scoped at design time: a visual nested tree in the World Book binder section (drag-to-reparent, expand/collapse); auto-linking or surfacing ancestors when a descendant is mentioned in prose (the roadmap's original note raised this as a possibility, explicitly not chosen). F-12 (world map) is now unblocked.

### 6. Escape as "back" (F-14) ✅

Small by volume, disproportionate by feel: Esc now pops one story-bible detour instead of doing nothing. Opening a glossary entry from a scene and hitting Esc returns to that scene; a chain (doc → entry → another entry) unwinds one step at a time, browser-style. Design settled 2026-08-02:

- **Doc↔entity hops only.** `selectDoc` and `showDoc` both _clear_ the stack rather than pushing to it, so choosing a scene in the binder is a fresh start. This was the roadmap's own flagged scope question, and the narrow answer is the right one for a writing app — "Esc took me to a different scene mid-draft" would be a genuinely alarming thing for a drafting tool to do, and it is a lot less state to get right.
- **`viewHistory: MainView[]` in the store**, pushed only by `showEntity`, popped by `goBack()` (which returns whether it went anywhere, so the key handler knows whether to `preventDefault`). Capped at 20 — restless clicking must not grow it without bound, and nobody presses Esc thirty times expecting an exact trail.
- **Three ways the stack is kept honest:** re-opening the entry already on screen is not a hop (no duplicate to step through twice); deleting an entry prunes it out of the history (otherwise Esc lands on the editor's "this entry no longer exists" state for something nobody asked to see again); and opening a different project resets both `mainView` and the history, so Esc can never walk back into the project just closed.
- **Dialogs still win.** `useFocusTrap` already stops Esc from propagating while focus is inside a dialog, but focus can go loose, so `App`'s handler independently checks for an open `.dialog-overlay` before navigating. Every dialog in the app renders that class, which makes one query cover all of them — including any added later — rather than a list of booleans that would silently fall out of date. Verified live: with a dialog open over an entry, Esc closes the dialog and leaves the entry in place; the next Esc then goes back.

**Found while building, not caused by it (I-10, since fixed):** `useFocusTrap` bound its Escape listener to the dialog root, so if focus was loose on `<body>` while a dialog was open, Esc did nothing at all and the dialog could only be dismissed with the mouse. F-14's overlay guard made that a no-op rather than a wrong action, but the gap was real and predated this work. The trap now also listens on `document` for the topmost dialog, which closes both halves of the story: dialog first, view-history pop only when nothing is open on top.

See the F-08 backlog entry for the shipped decisions: the twist/row-body split, `MainView`'s new `folder` case and its F-14 arrival semantics, the shared `loadAllDocs` loader, and the trash fallback.

**Also shipped, doc-only until now:** F-09 (focus mode) had already landed — zoom box, ⌥⌘F, the View menu item — but its roadmap entry was never flipped from 📋. Corrected in the same pass as F-08 rather than opening a doc-only PR for one status glyph.

### 8. Close project + a real home screen (F-24) ✅

The title-bar close-box (`App.tsx`) was decorative — a `<span>`, no handler — until now; it's a real `<button>` and closes the project, landing on `Welcome.tsx`, which gained a recents list.

- **The one real design fork — settled by asking, not assuming:** does closing a project also turn off `boot()`'s silent auto-reopen for the _next launch_, or only affect the current session? Chose the former: an explicit close clears `lastProjectPath` (`project:close` IPC handler), so the next launch lands on Welcome with recents to pick from — but quitting the app without closing first (⌘Q, or just closing the window) still auto-reopens exactly as before. Only the deliberate close action changes anything, which keeps the existing convenience intact for the common case (Geoffrey's own daily-use project) while making "close" mean close.
- **Recents are a separate, longer-lived list from `lastProjectPath`.** Deliberately: closing a project must not make it vanish from the very list meant to let you pick it back up. `main/wyrm/settings.ts` gained `recentProjects` (most-recent-first, capped at 8, title refreshed on every open in case the project was renamed) alongside the existing `lastProjectPath`, updated through the same `rememberProject` funnel every open/create path already called.
- **A moved or deleted project quietly drops off the list** the next time it fails to open (`project:openPath`'s existing "not a project" check now also prunes it), rather than sitting there as a dead row forever — same "handle absent gracefully" pattern as a deleted story-bible entry or a trashed binder node.
- Verified live: closed the demo project → Welcome showed a RECENT row for it → clicked the row → reopened to exactly where it was.

### F-01 · Local-only version control (no GitHub required) ✅ shipped

Users who want everything on their own machine must get full version-control parity — history, diff, restore, variants, branches — with no account and no network. WyrmStar already uses **isomorphic-git** (open-source, MIT), so the entire engine is local; GitHub is only a _remote_. Work needed:

- ✅ "No remote" is an explicit, first-class choice — the sync setup screen's first question, with local-only phrased as a peer of GitHub, not a fallback (PR #11).
- ✅ **Optional local backup target** — shipped in PR #10 (see Execution order §2). Note for whoever does the rest: isomorphic-git has **no local transport**, so this was built from git plumbing rather than `push`; GitHub sync gets a real HTTP transport and cannot reuse that code path.
- ✅ Sync surfaces degrade silently with no remote: Sync Now is disabled, the status bar shows plain `◆ LOCAL`, nothing nags (PR #11).
- ✅ **Every Phase 5 sync surface audited for the no-remote case.** Most already degraded correctly — Sync Now greyed out, the connected panel unrendered, auto-sync and the back-online retry no-ops, the status bar deliberately silent. The audit found one real fault, described below. Pinned by `tests/local-only.test.tsx`, which asserts the whole local-only state; nothing had covered it before, which is how the fault survived.
- ✅ **The trade-off is stated at the choice point**, per the brief's §7 instruction to call trade-offs out "explicitly during onboarding rather than burying it." The local-only panel says in plain words that this computer holds the only copy and a dying disk takes the history with it, and offers **Set Up a Backup…** directly rather than naming a menu item. A writer who already has a backup is told that instead, including the honest caveat that a folder on the same disk is not protection — the app cannot tell which physical drive a path is on. It never pushes GitHub as the remedy: local-only stays a peer choice, as PR #11 established.

**The fault the audit found — `mode` vs `remoteUrl` drift.** `SyncStatus.mode` is stored intent; `remoteUrl` is read live from `.git/config`. A remote removed outside the app leaves `mode: 'github'` with no URL, and the surfaces disagreed about what to do with that. The menu gated Sync Now on `mode` alone, so it stayed live and threw `This project is not connected to GitHub` as an unhandled rejection. The status bar read `mode` alone and reported `◆ SYNCED`. Only SyncDialog required both and correctly showed the reconnect form — so the app simultaneously claimed the work was safely off the machine and had no idea where to send it, which is the one lie an app promising "nothing is ever lost" must not tell. Fixed with one shared definition in `lib/syncState.ts` (`isConnected`, `isRemoteMissing`, `hasSecondCopy`) that every surface now uses; the drifted state reads as `◆ SYNC — NEEDS YOUR EYE`.

**Also fixed while there:** `syncNow` threw without recording anything, and its callers all fire it with `void` (the menu item, the post-checkpoint auto-sync, the back-online retry). A failed sync was therefore either an unhandled rejection or — had the menu simply added a `.catch` — silently swallowed, leaving the writer believing their work had reached GitHub. It now raises the existing quiet needs-attention flag before rethrowing, so a failure reaches the status bar instead of vanishing.

**Note:** this reorders Phase 5 slightly — local-first is the default path, GitHub sync becomes opt-in. Cheap to do now, expensive to retrofit.

### F-10 · Pins, tags & factions ✅ shipped — see Execution order §5a

Requested 2026-07-30, design settled 2026-08-01, built 2026-08-01. **This is the scene-level metadata model the roadmap was deferring.** F-02 (timeline), F-03 (plot graph) and F-04 (plotline tracking) all need exactly this and were explicitly held back so it would be designed once — see Execution order §5a for what shipped and what's still deferred (the skeuomorphic UI treatment). The design record below is kept as-is for context; F-02/F-03/F-04 can now proceed as views over this data.

**Pins and tags are two different mechanisms, not two names for one idea** — the original framing (both illustrated by the same four examples) blurred that, and it matters for the data model:

- **Pins are a closed, curated vocabulary the app ships**, scoped by what they're pinned to rather than one universal list — a pin only appears as an option where it means something. Documents get a scene-structural set (Rising Action, Climax, Setup, and similar — exact wording is a UI-copy pass, not a design blocker); characters get a narrative-role set (Protagonist, Antagonist, Viewpoint Character). World and glossary entities have no pin vocabulary of their own yet — nothing requested one, so none is invented; add one later if a real need shows up rather than filling the gap speculatively now.
- **Tags are a free vocabulary the writer invents**, no starter set, no fixed list — writer-owned the way the story bible already is.
- **Factions are not a third mechanism.** A faction is a tag, applied to `Entity` instead of `DocMeta`, following the exact same free-form rule — grouping characters, locations and glossary items into a named faction ("House Voss") is just several entities carrying the same tag value. This reuses the tag field rather than adding a parallel grouping concept, so `Entity` needs a `tags` field for the first time (it does not have one today) precisely so factions can exist. Note this only partly matches `design-brief.md`'s §5 aside that World entries might carry an internal `type` of "faction" — that was one entity being _labelled_ a faction; tags let _any_ entity, including characters, _belong_ to one. The tag reading is more general and is the one to build.
- **"Scene" is a tag, not a first-class document kind.** A document becomes orderable/plottable by carrying the tag `scene` — no new `BinderNodeType`, fully reversible, and every other part of the app (compile, search, the binder) keeps treating it as an ordinary document. F-02/F-03/F-04 filter on this tag to decide what counts as a plottable unit.

**Storage: document frontmatter, matching `DocMeta`/`Entity`'s existing shape** — versioned with the file, diffs cleanly, no second source of truth, and it is what the story bible already proves works. Losing the queryable-without-reading-every-file property that a `project.json` index would have given is an accepted, deliberate cost — matches "everything is plain text on purpose."

Concretely, once built:

- `DocMeta` gains `tags?: string[]` (free-form, including `scene`) and `pins?: string[]` (from the document-scoped fixed set).
- `Entity` gains `tags?: string[]` (free-form — factions live here by convention, no dedicated field) and `pins?: string[]` (from the character-scoped fixed set; meaningless and left empty on `world`/`glossary` entities for now).

Still open, deliberately left for the implementation pass rather than blocking design sign-off: the exact wording of each fixed pin list; the skeuomorphic UI (pins with actual pin heads, tags shaped like little luggage tags, still 1-bit) that the original request asked for; and how the binder/entity editor surfaces "add a tag" versus "add a pin" as two visually distinct actions given they are two different mechanisms now.

### F-12 · World map ✅ redrawn — a cartographer's surface, in four parts

**The map redrawn** (requested 2026-10-20). Geoffrey asked for the map to become a real cartographer's surface: a larger map area that scrolls and expands, land masses drawn as outlines, natural features (mountains, forests, rivers) as stamps, labels for those features, roads and railways, and borders or areas — all in the app's crunchy two-ink style. Planned as four PRs, each merged before the next: **(1) the map as a place** (shipped, below); **(2) land and borders** — land masses drawn as outlines point by point, with a dithered fill and an editable coast, and the same tool drawing borders and shaded areas; **(3) rivers, roads and railways** as 1-bit line styles; **(4) stamps and labels** — pixel-art mountains, hills, forests, marsh and towns, a name on any feature, and free labels for seas and regions. Every shape is its own small record, as pins and strings are, so sync merges them one by one; points are placed by click rather than drawn freehand, which suits the look and keeps files small.

**(1) The map as a place** (2026-10-20). It was a 640×380 dialog — room for a village. Now it takes the window as the corkboard does, binder hidden (`MainView` `{ kind: 'map' }`, a detour: Esc goes back). The map **scrolls**, **zooms** in whole and half steps (50/100/200%; anything between blurs the 1-bit strokes) keeping the middle of the view in the middle, and **pans** when the map itself is dragged. It **grows on any side** (More map: ↑ ↓ ← →) through `ProjectData.mapBounds`, an origin as well as a size: growing north or west moves the map's edge rather than every pin on it, so one field in `project.json` changes instead of a file per pin, and the view is moved by the same amount so nothing on screen jumps. A project that never grew its map gets a 2400×1600 default with the old dialog's area in its top-left corner, where every existing pin already sits. A dotted graticule every hundred map pixels, two-colour by being dotted rather than faint; past the map's edge is the desk dither. The **Places** list down the side places a location at the middle of what the writer is looking at, finds a placed one (scrolls to it and focuses its pin), and removes one. Pins drag as before, and nudge with ⌥+arrows (written once the keys stop). **Opening a place from the map is a detour** carrying the map's scroll, zoom and the pin, so Esc comes back to the map exactly as it was, the pin focused — waiting for the pins to load before it restores, which a test caught. One adversarial round confirmed sixteen findings, all fixed. **A pin move is written to the project it was made in** (`moveMapPinAt`, path-addressed, never creating a pin): a nudge still waiting when another window came to the front was written into that novel — a new pin pointing at nothing, or in a clone, that novel's real pin moved. Removing a pin cancels a nudge still waiting for it, which otherwise brought it straight back. **Deleting a place deletes its pin**, and a pin left over from before (or whose place has gone) still has a Remove in the list and opens nothing — the dialog could always remove one, and losing that was a regression. The pins are re-read when the project changes, not on every save, which raced a placement and could drop it. A cancelled gesture puts the pin back rather than opening the place. **Pins are drawn outside the scaled art**, so names and focus rings stay readable at 50% instead of 5px smudges. **The map is a keyboard place**: a named region the arrow keys move around (Shift further); zoom buttons keep focus at the ends of their range (`aria-disabled`, not `disabled`); Place moves focus to the new pin and Remove to the next row.

**(2) Land, areas and borders** (2026-10-21). Three drawing tools beside the Hand: **Land**, **Area** and **Border**, drawn point by point — a click puts a point down, a drag still moves the map, clicking the first point (or Return) closes a coast or an area, Return finishes a border, Backspace takes the last point back and Esc drops the shape without leaving the map. Too few points is said in the hint line, not silently refused. The **Hand** selects a shape — by pointer, or Tab and Return, each shape being a named button — and shows its corners and the middles of its edges: drag a corner (or Option and the arrows), click a middle to add a point, Delete on a corner to take one out (never below three for land and areas, two for borders; the hint says why), Delete on the shape to remove it, Esc to let go. Drawn in the palette's two inks: the **sea** is sparse ink dots on paper (the 25% dither was so dense it read as grey and hid the graticule), **land** is plain paper with an ink coast and short hachures offshore (a wide dashed stroke under the land, its inner half hidden by the fill — round caps swelled each dash into a blob, so the caps are square), **areas** are hatched with a dashed edge, **borders** the cartographer's dash-dot. ### F-15 · Manuscript mode ✅

Shipped. A vellum-and-iron-gall palette (`[data-palette='manuscript']`), a blackletter chrome face, a legible period serif for prose, and illuminated capitals chosen by the writer rather than applied to every paragraph.

**Fonts.** `@fontsource/unifrakturmaguntia` for chrome and the capitals, `@fontsource/cardo` for body prose — both OFL-1.1, both vendored as npm packages and imported in `main.tsx`, so they are bundled locally and work offline. Two faces, deliberately: the request was explicit that body prose stay readable, so Fraktur is atmosphere and Cardo does the reading.

**This is the first palette to change the prose font**, which is a genuine precedent — until now a palette only remapped colour and dithers, and the house rule "chrome uses the bitmap font" held universally. Both `--font-chrome` and `--font-prose` are now palette-overridable. A palette that repaints the prose face must keep it a reading face; atmosphere belongs in the chrome.

**The drop-cap rule is the writer's.** The opening paragraph always gets a capital, and so does any paragraph that follows a deliberate blank line — an extra Return. So an author sprinkles as many or as few as they like with a gesture they already know, and never learns a syntax. `lib/dropCaps.ts` marks them as a ProseMirror decoration rather than CSS, because `p:empty + p` cannot express the rule (ProseMirror renders an empty paragraph as `<p><br></p>`, not an empty element). The decoration runs under every palette and is gated entirely in CSS, the same reasoning as F-23's block cursor — recreating the editor on a palette switch would throw away undo history.

**Authored blank lines now survive the round trip.** This was the enabling change and the riskiest part of the work: `markdown.ts` previously collapsed any run of blank lines to a single paragraph break, so the gesture the drop-cap rule depends on was being silently discarded on every save. `markdownToDoc` now reconstructs empty paragraphs from markdown-it's `token.map` line ranges, and `docToMarkdown` emits exactly one extra newline per empty paragraph. The asymmetry matters: an earlier version of the fix wrote two newlines and read back one, which **grew the gaps on every save** (3 blank lines → 5 → 9). There is an explicit anti-inflation test pinning round-trip stability, and it is worth keeping — a serialization bug of this shape corrupts files quietly and cumulatively.

**Latent cascade bug found and fixed.** `data-palette` lives on `.screen`, but `font-family` was only declared on `body`, one level above. A custom property resolves where it is _used_, and inheritance passes the already-resolved value down — so the `:root` font was baked in before any palette could speak, and every chrome element that merely inherited kept Silkscreen while elements that re-declared the variable themselves switched. Half the chrome in one face, half in another. `.screen` now re-declares `font-family: var(--font-chrome)`; it is a no-op for every other palette. The same class of bug was already known and commented for `color`/`background` in the flat-palette block. Guarded by `tests/palette-fonts.test.ts`, which asserts against the stylesheet source because jsdom does not resolve custom properties through inheritance and a DOM test would guard nothing.

### F-23 · BIOS: block cursor in the editor pane ✅ shipped

Requested 2026-07-31, built 2026-08-04. A blinking block, BIOS-palette only, standing in for the native caret — confirmed a real CSS tweak wasn't enough (the experimental `caret-shape` property has no meaningful stable support), so this is `lib/blockCursor.ts`, a small ProseMirror `view` plugin.

- **A positioned overlay, not a decoration.** `coordsAtPos(selection.head)` gives real screen coordinates; the element is appended as a DOM _sibling_ of ProseMirror's own root (`view.dom.parentElement`), never a child — `view.dom`'s children are strictly reconciled against the document model, and a foreign node inside it would be fought over or silently removed on the next render.

Documents gain real pages — typing past the end of a page moves to a new one, and a finished page can "print" automatically (to PDF, matching the compiled manuscript, or to an actual connected printer), the way a page coming off a physical typewriter platen is simply done.

This is a substantially bigger piece of work than F-37 and touches capability areas the app has not needed before (OS print integration), so it deserves its own scoping pass rather than folding into F-37's PR:

- **What is a "page," concretely?** F-27 already flagged this exact question for its own dotted-rule page view and left it explicitly unresolved: real pagination depends on a paper size and font metrics, and "every N lines" is an approximation that will not match what the compiled `.docx`/PDF actually paginates to. This feature's whole premise is a _real_ page boundary (something to print), so the approximation F-27 could get away with is not available here — needs an actual answer, not a placeholder.
- **What does "print automatically" mean in practice?** Firing an OS print dialog the instant a page fills, with no writer confirmation, is a strong behavior to default to — worth confirming whether the request means literally that, or "make finishing a page one click from printed" (a nudge, not a silent trigger). The house rule that the writing terminal carries no notifications/interruptions cuts against anything that pops a dialog mid-sentence.
- **PDF export already has a natural home**: `lib/compile.ts` already flattens the binder into a format-independent block list for text/`.docx` export (brief §8) — a paginated PDF output is plausibly a fourth `CompileFormat` there rather than a new export pipeline, if the page definition above lands on something compile-compatible.
- **Real printer output is new ground for this app** — Electron exposes `webContents.print()`/`printToPDF()`, but silent/automatic printing (no dialog) needs a specific printer selected in advance and has real failure modes (offline printer, out of paper, wrong printer selected) that a "just works" feature can't quietly ignore. Worth deciding whether v1 is manual ("send this page to the printer" a writer clicks) before ever attempting the fully automatic version the request describes.

**Scoped 2026-08-12, split in two.** Answers to the questions above:

- **A page is Chromium's page, not ours.** Pagination happens at print time against a real paper size, using Electron's own print engine — the only page model that matches what physically comes out. No editor-side pagination was added; F-27's dotted rule stays the on-screen approximation it already says it is.
- **Auto-print reuses F-27's lines-per-page** as the "page finished" trigger. This resolves a real conflict: auto-printing needs a boundary the _editor_ knows about, which print-side pagination alone never provides. Consequence, accepted knowingly: a chunk is sized by line count, not paper metrics, so it may not exactly fill a sheet.
- **PDF is a fourth `CompileFormat`**, as predicted — `renderHtml` joins `renderText`/`renderMarkdown`/`docxBytes` as another pure function of the same block list.

**Part 1 ✅ shipped:** PDF export and manual printing.

- `renderHtml` produces standard-manuscript-format HTML (12pt monospace, double-spaced, 1in margins), which `compile:pdf` turns into PDF bytes via `printToPDF`, and `compile:print` sends to the OS print dialog. **File → Print Manuscript… (⌘P)**.
- Both render in a **throwaway offscreen window**, never the writer's own: `printToPDF` paginates whatever the window is showing, so reusing the main window would navigate the manuscript out from under them. Destroyed in a `finally` so a load failure can't leak a hidden window per attempt.
- Unlike `.docx`, PDF bytes can't be built in `compile()` — pagination is async and lives in main — so the store renders HTML and round-trips through IPC.
- `silent: false` on printing is deliberate for v1: the writer picks the printer and sees failures where they expect them.
- Degrades honestly in the browser preview: PDF export reports "PDF export needs the desktop app" rather than writing a file that isn't a PDF, and `printHtml` **throws** rather than returning `false` — false means "the writer cancelled", and reporting a missing print engine as a cancellation would leave ⌘P silently doing nothing.

**Part 2 ✅ shipped:** printer selection, settings, and the auto-print trigger.

- **Preferences → PRINTING**: "Print each page as it fills" (off by default) and a printer picker fed by `getPrintersAsync()`. New `PrintSettings`, app-level beside appearance and stats rather than folded into `AppearanceSettings` — a printer is not an appearance.
- **A page is F-27's lines-per-page**, the same number that draws the on-screen rule, so the page that prints is the page the writer just watched a rule appear under.
- **The safety property is that a page never prints twice.** Paper is physical and a runaway trigger is expensive, so `autoPrint.ts` tracks the _highest_ page ever completed and fires strictly above it. Deleting text lowers the live count and retyping raises it back through boundaries that already printed — those must stay silent. There is a regression test for exactly that, and it was verified to fail when the high-water mark is replaced with a live comparison.
- **A crossing emits every page at once**: a paste can cross several boundaries in one transaction, and firing only for the last would silently drop pages from the printout.
- **Auto-print requires a printer chosen in advance** and prints with `silent: true`. Printing silently to whatever the OS considers default is how paper appears from a machine nobody is standing at.
- **`printPage` never throws into the editor.** It fires mid-paragraph, where there is no safe place to interrupt; an offline printer is a printer problem, not a reason to break the writing surface (house rule: a failure in one panel never takes the app down).
- Pages are sliced from the live document and routed through the _same_ `runsFromParagraph` the compile pipeline uses (`blocksFromDoc`), so an auto-printed page renders bold/italic/highlight identically to the PDF. Extracting plain text would have been simpler and silently lost every mark.
- **Found while building:** `PrefsDialog` gained required props and two existing test files rendered it without them, crashing on `printers.map`. Fixed at both ends — the tests now pass the props, and `printers` defaults to `[]`, since a dialog hard-crashing on an absent list prop is precisely the "one panel takes down the app" failure the house rules forbid.

**Not verified end-to-end:** auto-print needs a real printer, which this machine's toolchain cannot exercise. The trigger arithmetic is unit-tested and Preferences is verified in the preview, but nothing has physically printed.

### F-39 · Real fullscreen, and Windows' doubled-up title bar ✅ shipped

Reported 2026-08-12, built the same day: on Windows, making the app "fullscreen" left both the taskbar and a window frame visible. Two separate causes, one of them a genuine platform bug rather than a missing feature.

- **There was no fullscreen feature at all.** Nothing in `src/` called `setFullScreen`, so what was actually being used was Windows' _maximize_, which by design keeps the taskbar and title bar. Added a real toggle on **F11** (the Windows convention) plus a **View → Full Screen** item. Deliberately its own toggle rather than folded into Focus Mode (F-09), which stays what it is — an in-window declutter that never touches the OS window.
- **Windows never got the macOS branch's treatment.** `main/index.ts` applied `titleBarStyle: 'hiddenInset'` under `process.platform === 'darwin'` only, so Windows drew a native title bar _on top of_ the app's own retro menu bar — two chrome bars, Windows-only, since the first release. Now `titleBarStyle: 'hidden'` plus `titleBarOverlay`, which removes the frame while keeping real minimize/maximize/close. `.menu-bar` was already `-webkit-app-region: drag` on every platform, so the window stayed movable with no extra work; `.is-electron-win .menu-bar` just gains right-padding for the caption buttons, mirroring the existing left-padding for macOS traffic lights.
- **The overlay's colours are read out of the live DOM, not mapped in TypeScript.** `retro.css` is the single place a palette's `--ink`/`--paper` is defined (house rule), and a second copy in main-process code would drift the first time a palette was retuned — so the renderer reads the computed values off the themed element and passes them over IPC. `TITLE_BAR_OVERLAY_HEIGHT` is the one unavoidable duplication (main can't read the stylesheet) and carries a comment tying it to `.menu-bar`'s 30px.
- **F11 is deliberately not intercepted outside Electron** — the browser preview's own F11 already fullscreens, and swallowing it would remove a working shortcut for nothing. There's a regression test for exactly that, since it's the kind of thing a later refactor "tidies" away.
- **Not verified on Windows.** Built and tested on macOS: the suite covers the wiring (F11 reaching the API, the not-swallowed-in-browser rule, the menu item being reachable with no project open), and the browser preview confirms the menu renders — but the actual Windows chrome and taskbar behaviour can only be confirmed by running a Windows build. Worth a look before assuming the caption-button padding (138px) is right at non-100% display scaling.

### F-40 · Back up to several locations at once ✅ shipped

Requested 2026-09-24: "select multiple backup locations (say, GitHub AND a storage card) and sync to all." Backup settings were a single `path`; they are now a list of targets, and every checkpoint writes to all of them.

**GitHub stayed a separate axis, deliberately.** The obvious reading of the request is one unified "destinations" list with GitHub as a row in it, and that was considered and rejected: GitHub is genuinely a different thing — auth, conflicts, merges, and a _pull_ rather than only a push. Flattening it into a folder-shaped row would hide that a conflict needs a decision from the writer. Local targets are a list; GitHub sync is still GitHub sync. The two are presented together in the Sync dialog's local-only panel, which is where the question "where does my work actually live" gets answered.

**An unreachable target is a skip, not a failure.** A storage card is usually not plugged in — that is the normal state of removable media, not a fault, and treating it as an error would raise the needs-attention flag most days and train the writer to ignore the one signal that matters. `isReachable` asks a narrow question (does the folder exist, or for a first backup does its parent), because an unmounted volume takes its whole mount point with it. A target that exists but cannot be written _is_ reported as a failure, because that is a real one.

**Targets are independent.** One unplugged card cannot stop the external drive being written, and neither can one genuinely broken target: every target is attempted and every result reported, rather than the run stopping at the first problem. Each target carries its own `lastBackupAt` — the whole point of several is that they fall out of date separately — so the panel shows which copies are current and which have been out of the building since Tuesday. That per-target staleness is the honest answer to "am I covered", and it is visible on demand rather than announced.

Runs are sequential on purpose: these are large object copies to often-slow media, and `backupProject` begins by committing the working tree, so running them concurrently would have several mirrors racing the same `commitAll` against one repo.

**Migration was the risk.** A writer with a drive already configured must not silently lose it — that would leave a project with no second copy while the status bar still read `◆ LOCAL + BACKUP`, exactly the class of lie F-01 had just finished removing. The legacy `{ path, auto, lastBackupAt }` shape is upgraded on read, keeping the path _and_ its last-backup time, and the upgrade also runs before any patch is applied so toggling automatic backup cannot drop the drive. Migration happens on read rather than in a one-shot pass because there is no moment we control when every project's settings are loaded — a project may go untouched for months.

**Found while testing:** `tests/backup-store.test.tsx` was only isolated by accident. The mock api keeps backup settings in a module-level map that outlives a test, and the suite happened to pass because whichever test ran last cleared the location. Adding a test that deliberately left automatic backup on exposed it. The teardown now resets that map explicitly.

### F-41 · Several projects open at once ✅ shipped

Requested 2026-09-24: open a second project inside the same instance, drag the windows around the desktop, tab between them, minimize them to icons, and have the close box shut one project rather than the app.

**Settled before any code:** dialogs stay app-modal and act on the focused window (per-window dialogs would mean re-parenting all fifteen and restructuring the documented z-index budget, for flexibility nobody has asked for yet); the title bar gains a **third box** for minimize, with zoom keeping its current Focus Mode meaning so no existing control changes under the writer; and **opening an already-open project raises its window** rather than opening it twice — two editors on one `documents/<id>.md` would race autosave and git against the same repo, and nothing serializes that today.

**Planned order**, store first and pixels last: per-project runtime → per-project state slice → N windows at fixed geometry → drag, stacking and focus → dialogs → minimize to desktop icons.

#### Step 1 — per-project runtime ✅ shipped

The debounced save, the five-minute Autosave interval and the dirty flag were module-level singletons. That was correct for exactly as long as one project could be open, and becomes silent data loss the moment a second window exists:

- a keystroke in B cleared A's pending 800 ms save, so A's flush never fired and the draft sat unwritten;
- opening B called `clearInterval` on A's auto-commit, so A quietly stopped checkpointing;
- one shared dirty flag meant a commit in A marked B's unsaved work as already checkpointed — the same class of bug `git.ts`'s blob-hash comparison exists to prevent, work that looks saved and is not.

All three now live in a `ProjectRuntime` keyed by project path, which is the identity the main process already uses everywhere. Behaviour with one project is unchanged by construction, and `disposeRuntime` runs on close so neither an interval nor a map entry outlives its project.

The auto-commit callback carries an explicit routing guard: today it is always true, because only one project can be open, and it is the seam step 2 builds on.

**State was deliberately left flat in this step.** The tempting middle path — reshape into `projects: Record<path, slice>` while mirroring the focused project's fields at the top level — was rejected: the mirror needs all ~40 `set({…})` sites converted to write through a helper anyway, which is the same blast radius as the full reshape, plus a silent-divergence mode whenever a site forgets. Step 2 found a shape with neither cost.

#### Step 2 — per-project state ✅ shipped

Each open project's state is now its own. **No pixels move** and no user-visible behaviour changes: nothing yet opens a second project, because there is nowhere to show it. What exists is the state machine the windows will sit on.

**The focused project's state stays in the flat fields; the others are parked by path** (`parked: Record<string, ProjectSlice>`, plus `openPaths` in window order). Focusing swaps — the current fields are parked under their path and the target's are lifted out. This was chosen over the more obvious `projects: Record<path, slice>` with everything addressed by id because there is exactly **one home for each project's data and nothing is mirrored**, so no two copies can drift; because every action keeps acting on "the" project, which is the focused one, matching the settled decision that dialogs are app-modal and act on the focused window; and because it left all ~40 store call sites and all 259 test pokes working unchanged, so the diff is the state machine rather than a rename across the codebase.

`SLICE_KEYS` is the single declaration of what belongs to a project — `ProjectSlice` is `Pick`ed from it, so the type and the code that copies state in and out of focus cannot disagree. Everything absent from it is app-level: appearance, stats and print settings, typewriter mode, recents, `booted`.

**`editor` is never parked.** It is in the slice, but always stored as `null`: the TipTap instance belongs to the component that mounted it, and by the time a project is focused again that component has unmounted and destroyed it. Restoring the handle would hand back a corpse. Per-window editor registration is step 3.

**Closing gained cases.** `closeProject(path?)` closes the named project or the focused one. Closing a background project leaves the focused one untouched. Closing the focused project brings the most recently opened of the rest forward, rather than dropping the writer to the home screen while they still have projects open. Only when the last project closes does `api.closeProject()` run — turning off auto-reopen once, not every time a window shuts.

**Fixed in passing:** `tagFilter` and `dailyStats` were never reset when a project closed, so they leaked into the next project opened. They are in the slice now, which fixes it by construction.

**A background project still checkpoints.** Its interval fires, but `commitNow` acts on the focused project, so routing it there would have meant an open-but-unfocused project silently never writing history. `commitParked` handles it: nothing to flush (a project's pending save is flushed as it loses focus, and it has no window of its own yet), the commit is already path-addressed in the main process, and the bookkeeping lands on the parked slice rather than on the flat fields, which hold a different project entirely. Background _backup_ and _sync_ for parked projects are not wired up yet — they follow in step 3, where a window makes a project properly present.

**Still to come:** `openAdditionalProject` is implemented and tested but wired to nothing — opening a second project with no way to see or reach it would be worse than not offering it. Step 3 gives it a window.

#### Step 3 — a window per project ✅ shipped

The first visible step. **File → Open in New Window… (⇧⌘O)** opens a project alongside the current one, and the desktop draws one `.mac-window` per open project, cascaded 28px down-and-right so each frame stays reachable. A lone project keeps the full-bleed layout it has always had — cascading one window would shrink the page for nothing.

**The front window is the app; the others are snapshots.** Only the focused project has live state (step 2), so a background window renders from its parked slice: its manuscript as a page of text, with no caret and no selection. That is deliberate rather than a limitation to apologise for — it reads as the document it is while never inviting keystrokes that would land in a different novel. Clicking anywhere in it brings it forward, at which point it becomes the real thing, editor and all. Classic Mac drops the title-bar pinstripes on inactive windows for the same reason, and that styling is restored here: two identical frames otherwise give the writer no way to tell where their typing will go.

**Each window's close box closes its own project**, not whichever is focused — with a cascade of identical frames, closing the wrong novel would be silent and would look unrecoverable. The box stops its own mouse events so it cannot focus the window on the way to closing it, which would also route the close through a different code path than the one intended.

**Stacking stays inside the documented z-index budget.** Project windows sit far below `.menu-drop` (90), so a menu is never trapped behind a window, and nowhere near `.dialog-overlay` (300) — which is what keeps dialogs app-modal across every window, as settled up front.

**Fixed in passing:** ⌘O has been printed beside _Open Project…_ since Phase 2 with nothing bound to it — it silently did nothing. Implemented rather than adding a second decorative shortcut beside it.

**The honest edge:** in a cascade, which part of a background window is exposed depends on where it sits. A window earlier in the stack shows its title bar; a later one shows the strip along its bottom. Both are clickable, and the strip names its project for exactly that reason — but it is a fixed-geometry compromise, and step 4's dragging is what properly resolves it.

**Not done here:** dragging, resizing, minimize-to-icon, and background backup/sync for parked projects.

#### Step 4 — dragging, resizing, stacking and focus ✅ shipped

Windows can be dragged by their title bar and resized from a classic bottom-right grow box, and **positions persist** — per project path in settings, so reopening a novel puts its window back where it was left.

**The arithmetic is pure and lives in `lib/windowGeometry.ts`.** Dragging and resizing are exactly where a sign error strands a window somewhere the writer cannot click — above the top edge there is no title bar left to grab, far enough sideways there is nothing to grab either, small enough and the close box stops existing — and none of those are recoverable from inside the app. jsdom has no layout engine, so a test going through real elements could check none of it. The pointer handlers feed deltas into pure functions instead, and `tests/window-geometry.test.ts` exercises the rules directly.

**`openPaths` became stacking order.** Position is explicit now, so moving a path to the end raises that window without moving anything on the desktop. That resolves step 3's compromise, where which part of a background window you could click depended on where it sat in the cascade.

**Three bugs found while building it, all in the same family — trusting a measurement or an event that was not there:**

- **A window sized from an empty desktop.** `.desktop` has 14px of padding, so before any project renders it measures exactly 28×28, and the first window was placed from that: a 28-pixel square that cannot be read, clicked or resized back. Measurements narrower than a window's own minimum are now rejected, placement waits for a believable one, and a re-clamp on every desktop change heals anything already stored — which also means shrinking the app window can no longer strand a window outside it.
- **`preventDefault()` on pointerdown suppresses the compatibility mouse events.** The drag handler calls it, so clicking a background window's title bar silently failed to raise the window, because focus was listening for `mousedown`. Focus moved to `pointerdown`.
- **The grow box had to pick a side.** Raising a window swaps the store's focused slice, which unmounts the component mid-gesture and kills the drag. So a corner grab now stops propagation and resizes in place, while the title bar deliberately does the opposite and raises — that being the main way to bring a window forward.

**Resizing never shrinks a window to satisfy the desktop edge.** A window dragged mostly off the right is a position clamping allows, so its width already extends past the edge; capping growth at the edge would have yanked it narrower the moment its corner was grabbed. Found by a test, not by inspection.

**Two tests were vacuous on the first pass** and only admitted it under injected regressions: one stubbed `setPointerCapture` on the button rather than the element the drag handler actually runs on, so the drag died on a missing method instead of being blocked; the other asserted synchronously against an async `focusProject`, checking before the thing it forbade could have happened.

**Reported after the first build, and fixed: a window could end up unreachable.** Dragging and frame-resizing both clamp correctly — that was verified — but a _restored_ position was not. Reopening a project on a smaller screen than the one it was last arranged on put its window outside the frame, and the clamp only watched the desktop size, which has not changed since the app started. It now watches the geometry as well, so any position entering state is checked wherever it came from.

Two further bugs fell out of fixing that. `useDesktopSize` returned a freshly-built object on every render while falling back to the viewport, so every effect depending on it re-ran constantly — wasteful, but worse, it hid the dependency bug above by papering over it, and the test for the fix passed against the broken code until the identity was made stable. And **Clean Up Windows forgot the positions without laying the windows out again**, because the placement effect did not watch the geometry either — recovery would have left the writer with no windows at all.

**`View → Clean Up Windows`** is the guaranteed way back, independent of cause. Clamping is meant to make a stranded window impossible, but "meant to" is not good enough when the failure mode is a novel you can see and cannot click, so there is a recovery that needs no diagnosis. It clears the remembered positions on disk too, or reopening would restore the very arrangement the writer just asked to be rid of.

**Not verified live:** persistence across a restart. The preview's mock keeps geometry in memory only, so the round trip is covered by tests and by the settings layer rather than by hand.

#### Step 6 — minimise to desktop icons ✅ shipped — F-41 complete

A third title-bar box collapses a project to an icon on the desktop; clicking the icon brings it back as the focused window. Classic Mac had two boxes, but Focus Mode already owns the zoom box, and changing what an existing control does would be worse than being one glyph less period-correct.

**A minimised project is still open.** Its state stays parked and its background work keeps running — it simply is not drawn. That distinction is the whole point: if minimising quietly stopped a project checkpointing, backing up and syncing, a writer tidying their desktop would be switching off the safety net without being told. There is a test for it, and one asserting that minimising the last window never calls `api.closeProject` — minimising is not closing, and it must not change what reopens next launch.

**Minimised state is deliberately not persisted**, unlike window positions. Minimising is a "get this out of my way for now" gesture; reopening the app to find a novel reduced to an icon would be a surprise rather than a convenience.

**Icons are auto-arranged along the bottom, not draggable.** Free placement would be more faithful to a real desktop, but it introduces the one thing windowing must never do — put something where the writer cannot find it — and a row that is always in the same place costs nothing to look at. A single click restores: classic Mac wanted a double-click because the first click selected the icon, and with no selection here to compete with, a hidden second click would be a gesture nobody discovers.

**The strip is layout, not an overlay**, which took two attempts. Floating it over the desktop covered the status bar — word count and save state — of any window reaching the bottom, and a lone full-bleed window ignored the measurement entirely because `.main-window` positions itself with a CSS inset. `.desktop` is now a column: a windows area that `useDesktopSize` measures, with the strip beneath it. Windows clamp above the icons by construction rather than by arithmetic.

**Minimising every window leaves a bare desktop with icons**, not the home screen. The home screen would say there is no project open, which is untrue and would invite opening a second copy of one.

#### Step 5 — dialogs and the project under them ✅ shipped

The settled design holds: dialogs stay app-modal and act on the focused project. What needed fixing was the gap that opens once several projects can be focused.

**The menu bar sits above the dialog overlay** in the documented z-index budget — 310 against 300 — which is deliberate and predates this work. The consequence with several projects is that the project _underneath_ an open dialog can change while it is open, via `File → Open in New Window` or ⇧⌘O. Dialogs read the focused project live, so the dialog silently retargets. Confirmed by hand before fixing: with Compile open for "Novel 1", opening a third project left the dialog on screen, now pointed at "Novel 2" — and compiling would have exported the wrong novel with nothing on screen to say so.

**A dialog now belongs to the project that was in front when it was opened**, and a focus change closes it. The writer re-opens it against the project they can actually see, rather than acting on one they cannot. The alternative — pinning each dialog to a project and letting it outlive a focus change — would mean a dialog acting on a window that is no longer in front, which is the same confusion wearing a different hat.

**About is deliberately exempt.** Nothing about it is project-scoped, so dismissing it when a window changes would just be rude.

**Noted, not fixed:** the menu bar remaining live over a dialog means project-scoped menu items still act on the project behind it — `New Document` while Compile is open, for instance. That is pre-existing and equally true with one project open, so it is a separate question from this step rather than part of it.

#### Background backup and sync for parked projects ✅ shipped

Step 2 gave a parked project its own checkpoint but not its own backup or sync, so two novels could sit open all day and only the focused one would ever leave the machine. Both now follow a parked checkpoint, read from that project's own slice, and are fire-and-forget exactly as they are for the focused project — a missing drive or a dead network must never block a checkpoint.

**Syncing a background project introduced a second hazard, and it is the more dangerous one.** Sync is bidirectional: a background sync can _pull_, changing the files on disk while the parked slice still holds the binder and open document from before. Focusing that project and typing would write stale text over work that had just arrived from another device — silent loss of exactly the kind the app exists to prevent, and newly possible only because background sync now exists.

So a pull or a merge marks the slice `stale`, and `focusProject` re-reads from disk before the writer can touch it, via the `reloadAfterRemoteChange` that already existed for this job — which keeps the open document rather than dropping them back to the first scene. A push changes nothing on disk and is left alone.

Conflicts from a background sync raise the quiet needs-attention flag on that project's slice and never put a dialog on screen: the page is sacred, and only a sync the writer asked for may interrupt.

**Deliberately not done:** a push-only mode for background projects, which would have side-stepped the staleness question entirely. `syncProject` has no such mode, and adding one would mean a background project that pushes for hours and never learns what another device has been doing — the staleness would still be there, just unacknowledged.

**Testing note.** None of this is reachable through the UI yet, so each test stands a second project's runtime up directly. Two of the four guards were initially vacuous and were caught by injecting the old singletons back: comparing a stored timer handle before and after cannot detect cancellation, because `clearInterval` stops a timer without changing its handle, and `expect(undefined).not.toBeNull()` passes — so a test asserting `__runtimeFor(OTHER)?.commitTimer` survives the entry being disposed entirely. Both now assert behaviourally with fake timers: does the other project still tick?

### Corkboard ✅ shipped — Phase 6's last item

Every scene in the project as an index card, pinned to a cork desktop — and, since F-45, the characters and locations put there too. Clicking a card opens it; dragging one places it, and Apply Order is what writes an arrangement back to the manuscript.

**Cards are placed, not flowed.** A card stays exactly where it is dropped, and the position is stored on the scene itself (`boardX`/`boardY` in its frontmatter), so it survives leaving the view, closing the project and syncing to another machine. A card nobody has moved has no stored position at all and falls back to its slot in **binder order**, so a project that has never used the board reads exactly as it did before placement existed and nothing is written to any file until a card is actually moved.

**Tidy had to re-read the documents, and did not** (fixed 2026-10-15, reported: _"the first card snaps to the correct spot, but the second card always snaps to around the middle"_). The board reads documents once when it opens, and clearing a position does not change `project`, so nothing re-read them: Tidy wrote the cleared positions to disk and then fell straight back to the stale copies still held in the view. A card that had never been moved went to its slot correctly; every card that _had_ a stored position sprang back to it — which is exactly the half-right behaviour reported.

Placement gets away without a re-read because it holds the new position in the component until the write lands. Tidy cannot, since the stored positions are the thing it clears. The regression test writes a position **before the board renders**, which is what makes it the real case: the earlier test dragged a card first, so the stale documents predated the drag and happened to be correct — it passed against the bug.

**Tidy is the way back.** Free placement means a board can end up in a state only its author understands, so the tool strip carries a Tidy button that clears every stored position and returns the cards to binder order. It is disabled until something has actually been moved.

The tidy grid is **as square as the cards allow** rather than as wide as the board — `ceil(sqrt(n))` columns, capped by what actually fits. Filling the width first put a handful of scenes in a single row, so Tidy read as snapping cards into line rather than laying a board out: the grid was there, but nothing in the result showed it. Four scenes now land as a 2x2, nine as a 3x3, and the reading order is still left-to-right in binder order.

**Dragging no longer reorders the manuscript**, which reverses this entry's original decision. The board shipped as "the binder seen as cards", where moving a card moved the scene — but in use the thing a writer wants from a corkboard is to _arrange_, and a card that reordered the manuscript and then snapped into the grid never stayed where it was put. Those two readings of a drop cannot both own the gesture. Placement won it; the binder is still the book, and it is still how the manuscript is reordered. F-02's distinction holds either way: the timeline has `timelineOrder`, the board now has positions, and the binder has the narrative order — three questions, three answers, none of them derived from another.

**Apply Order** (shipped 2026-10-18; the first of the refinement → polish → new-feature rotation Geoffrey asked for that day) is the other half of "arrange, then commit": a button on the strip reads the scene cards row by row, left to right, and puts the scenes in that order in the manuscript. **Rows are found by clustering, not by a grid** — a card is on the row of the one before it if its top is within `ROW_TOLERANCE` (60% of a card's height) of the row's _first_ card, because a hand does not lay cards on a grid and a card set a little lower is still on the same row to the eye; a card more than that far down is the next row, and measuring from the row's first card rather than the previous one is what stops a staircase of cards chaining into one backwards row. **Within a folder, never across** — the board does not show folder structure, so a scene is reordered among the scenes of its own parent and the fixed nodes (folders, notes, untagged docs) keep their exact indices; silently moving a scene into another chapter is not something a writer asked for by arranging cards. For the same reason **the button asks its question per folder**: an arrangement that differs only across folders is one applying could not change, and a button that offers to apply an order the book already has, or one it cannot give it, lies about having something to do; the store returns null and writes nothing in that case. **Never while stacked** — the piles are a way of looking, and the order they would read in is the cascade's geometry, not the writer's arrangement (the adversarial review found the button enabled the moment a card was pulled from a pile, and that it would have written the pile's 24px cascade into the binder). **Applying pins every scene card where it sits**: unmoved cards sit in slots dealt by binder position, so once the binder changed they would have been re-dealt, the board would have read differently from the order just applied, and the button would have lit up again at once; every unplaced scene is placed at the slot it was in, before the write lands so that nothing jumps, which is also what "apply this arrangement" means — and the one time the board writes positions for cards nobody dragged. **Undo Apply re-applies the order from before, not a snapshot — and only for the folders Apply changed.** The first version put back a copy of the whole binder, and the second review round showed what that drops: a scene added with Add Card in between vanished from binder and trash with its file orphaned on disk, and a chapter another device had synced in would have been reverted. The second version re-applied the order of _every_ scene, and the third round showed that reverting folders Apply never touched — a chapter reordered by hand since, or by another device — and re-ranking a scene moved to another folder in between. `applyBoardOrder` now returns what it changed: one entry per folder it reordered, with that folder's scenes in their pre-apply order, recorded in the store **before the write** so a save that throws still leaves a way back; Undo re-applies those entries, each kept to the scenes still in that folder. It is per project (`boardUndo` in `SLICE_KEYS`) so it survives leaving the board, which is the first thing a writer does after applying — and `loadProject` clears it, because left over it lit the button in a novel nothing had been applied to, and in a clone or restored backup (which share the original's ids) pressing it would have rewritten that copy's binder. Characters and locations take no part. **The pins are written by the same store call as the binder** (`applyBoardOrder(orderedIds, pins)`), which captures the project once. The save is an await a writer can click another window across, and the fourth review round found the pin writes reading the _focused_ project's open document per card — for a clone or a restored backup, which share the original's ids, the other novel's text would have been written into this one's file — and `persistProject` dirtying whichever project was in front once its save resolved rather than the one it saved. `writePositions` now looks the open document up wherever it lives at that moment, flat fields or parked slice; Undo's clear got the same treatment and runs in a `finally`, because a failed save had left a _redo_ on the button. **Dealing skips covered slots**: after Apply every card is pinned at the slots of the column count the board had then, and a scene added afterwards is dealt at the count it has now — at a square number (four cards to five) that is exactly where a pinned card sits — so a dealt card whose slot is more than half under a placed card takes the next free one, and the cards dealt after it shift along.

**The board, per palette** (2026-10-19, the rotation's first polish pass). The red string and the grey portraits were one treatment laid over sixteen palettes, and on seven of them the red fell under 3:1 against the paper — on Blueprint's blue it was 1.7:1 and all but vanished into the cork. Each palette now draws them in its own terms. **One-colour screens have no red to give**: Green, Amber, Vaporwave and Virtual Wyrm draw the string in their phosphor with a glow. **Blueprint draughts it** as a white dashed construction line. The dark grounds get reds that hold up, from the machine where there was one (CGA light red on BIOS, the NES red on Famicom, Win95's system maroon). **Portraits print as a duotone in the palette's two inks** rather than in greys — a grey photograph on a green-and-gold page was still a sticker from another app — with the darker ink in the shadows, so light-ink palettes swap the pair; Halftone also screens them into dots. `tests/palette-fonts.test.ts` resolves every palette's string and duotone through the cascade, holds the string to 3:1, and fails a portrait that would print as a negative. The browser preview's stand-in portrait became a colour head-and-shoulders over a gradient, since a single pixel shows nothing of a duotone.

**A card shows** title, the folder it lives under, the opening of the scene in the prose face, its word count and status — and says _"Not written yet."_ rather than showing a blank card, which is the state every outlined scene will start in (F-42).

**Scenes are scene-tagged documents**, identified exactly as every other view identifies them. Deciding that a second way here is how views drift apart.

**Labelled strings, and relationships as string** (2026-10-20, the rotation's second new feature). A string can now say what it means, on a tag at its middle (`stringMidpoint`: halfway along the hanging curve). After the second pin the string is not made at once: a label field opens where its tag will be; Return makes it (a bare Return makes a plain string, with no label key on disk), Esc pulls it back, and clicking away keeps what was typed. With the string tool up every tag is a button that reopens the field. **A string between two characters is a relationship**, not a board string: it goes in the Character Graph (`createRelationship`), so its name is required, and an empty Return says so rather than silently refusing. The other way round, **every relationship whose two characters are both on the board is drawn as string** (`relationshipStrings`) — derived from the relationship, never stored as a board string, so the cast graph and the board are one set of data seen twice: rename it from its tag and the graph has the new name; pull its pin and the relationship is gone from both (the history keeps it). A relationship with one character off the board is hidden, never removed. These strings meet the cards at the **middles of the edges that face each other** (`facingPins`): pinned top to top, a string between two cards in a column ran through the upper card and its label sat on that card's text. The tag carries the direction the relationship reads (`directedLabel`), along the string — ↓ or ↑ when it mostly runs that way. Board strings' labels are read and written field by field in `main/wyrm/boardStrings.ts`, omitted when blank. One adversarial round confirmed fifteen findings, all fixed. **Two relationships between the same pair** ("sister of" one way, "brother of" the other — the ordinary case) drew on the same line with stacked tags, only the top one reachable; each is now moved off the shared line by its place in the pair (`PARALLEL_SPACING`), and the same relationship twice in one direction is refused with a message saying where the first is. **The label field holds when the window loses focus** (Cmd-Tab no longer saves a half-typed name into the Character Graph), an unnamed relationship stays open with its reason rather than taking both pins with it, and a click on a card while a string is being named goes back to the field. **A tag on a short string no longer covers its pins** (`tagPlace`: beside a short string that runs down, above or below the cards for one that runs across, a pair's tags on opposite sides). **Strings pinned from the keyboard meet the facing edges** too. An unchanged label writes nothing; clicking the next card no longer pulls focus back to the last; a tag with the tool down tells a screen reader who it joins, with the arrow kept from being read aloud.

**The board from the keyboard** (2026-10-20, the rotation's second polish pass). The board was mouse-only: Tab reached the cards but nothing could move one, the string tool had no key path, and Add Card had no shortcut. **Arrows go to the nearest card that way** (`nearestCard`: centres compared, a 90° cone so ↓ never lands beside, and distance along the axis plus twice the sideways offset, so a card straight ahead beats a nearer one far to the side) — Tab still goes in binder order, which on a free-form board can be anywhere on screen. **⌥+arrows nudge** the card 8px, ⇧⌥ a bigger step, through the same `placeCard` a drag uses, so a nudged card in a pile is pulled out of it exactly as a dragged one is. **⇧Return turns a scene card over.** With the string tool up, **Return on a card pins it at its top centre** — a keyboard click has no pointer position (`detail` 0), so it pins where a hand would without thinking — and a screen-reader status line says a pin is waiting. **Pins become focusable buttons only while the tool is up**, named for the two cards the string joins, and Delete pulls one, leaving focus on the card it ran from. **⌥⌘N opens Add Card from anywhere**, bringing the board up; it is in the Corkboard menu and the command palette too, and its open state moved into the store (`addCardFor`) so all three can reach it, cleared whenever the project in front changes. ⌘N and ⇧⌘N now ignore Option, so Ctrl+Alt+N on Windows (which reports the key as "n") no longer makes a document. The ⌘/ legend has a new "On the corkboard" group. One adversarial round confirmed twelve findings, all fixed. **Add Card no longer opens over another dialog** (⌥⌘N and the menu now check, since its focus trap would have taken the keyboard into a form hidden behind the one on screen), and **leaving the board closes it** — a store subscription, since the state no longer unmounts with the board and StrictMode would have run an unmount cleanup on the first mount. **Esc closes a dialog over the board even with the string tool up**; the tool's capture-phase listener now yields to any open dialog. **A held ⌥+arrow writes once**, 300ms after it stops (written at once if the board goes away first), so writes cannot land out of order, and the view follows the card. **Focused pins show a ring** and thicken their string. **After Add Card, the keyboard lands on the card it made** — but only once the key that closed the dialog is released: the preview showed the Return that made a card being delivered to that card's button the moment it had focus, opening the new scene and leaving the board.

**Esc from a card goes back to the board** (2026-10-19, the rotation's second refinement). Opening a scene from its card used to be an arrival, exactly like picking it in the binder: Esc's history was cleared, so Esc from the scene did nothing, and the writer had to find their way back to the board and then to the card they were on. That was deliberate before outline mode, to avoid Esc behaving differently depending on how a scene was opened. With the back of the card shipped, the board is where a story is worked through card by card, so a card is now a detour: the board view it was opened from becomes the one step Esc goes back to (`selectDoc`'s `returnTo`, `showEntity`'s `from`), carrying the card and how far down the board was scrolled. Coming back, the board waits until it has measured its width, so unplaced cards are already in their final columns, then restores the scroll and focuses that card. A card gone since (untagged, trashed) still lands on the board at the old scroll. Picking a scene in the binder from there is still an arrival and clears the trail, so Esc never drags a writer back to a board they have moved on from. The adversarial review confirmed nine findings, all fixed. **The place is a one-off**: the board clears it from the view as it uses it (`settleBoardReturn`), because left there, every later remount of the board — after Writing Stats, after another project's window was in front — snapped back to that old card. **On the page in Focus Mode, Esc leaves Focus Mode first**, keeping the way back to the board for the next Esc; drafting in a scene opened from a card for an hour must not end with Esc swapping the text for the board. **A stacked board comes back stacked**, with the same cards pulled out, since the scroll was measured in that layout. **Esc that a control has used no longer also goes back**: the binder rename, the story-bible panel's name field and the menu bar now stop the key, so cancelling a rename does not also leave the scene. That is a stop, not a check of `defaultPrevented` — ProseMirror prevents the default of every Esc pressed in the editor, used or not, and the first version of this fix stopped Esc going back from the page at all.

**The board replaces the manuscript view rather than sitting beside it.** The binder is the manuscript as a list and the board is the same scenes as cards, so showing both at once is the same information twice. With the binder hidden, the timeline, plot graph and world map are pinned to the board as notes of their own — which is the unification F-42 is after, made literal: the same scenes seen as a line, a curve and a map, reachable from where they live rather than from a menu.

**It is a `mainView`, not a dialog** — a place to work from, like the folder view and stats page, rather than something glanced at mid-sentence. Opening it clears the view history the way `showFolder` does, and clicking a card is an arrival like picking a scene in the binder. Whether the board→scene→board loop deserves its own Esc path is left until outline mode exists and the loop actually matters; inventing one now would mean Esc behaving differently depending on how a scene was opened.

**Skeuomorphism, per palette.** Cork is a `--cork` grain declared alongside the dithers and scrollbar arrows, and **all sixteen palettes restate it with their own ink** — it was first declared only at `:root`, which meant every theme drew black grain regardless of its colours, exactly the drift the restate-every-data-URI rule exists to prevent. `tests/palette-fonts.test.ts` now fails, naming the palette, if one is missing or drawn in the wrong ink.

The grain took three passes. A fine, evenly spaced speckle read as a dither; scaling that up read as polka dots, because uniform flecks on a regular lattice are a different material entirely. Hand-placing flecks then scaled the problem up with them: magnifying a 32px tile to 56px magnified every fleck, and the positions I chose by hand still lined up into diagonals. The tile is now 96px, drawn at its own size so a 1px fleck stays 1px, with positions generated by rejection sampling — a minimum distance apart measured with wrap-around, so the tile's own seams do not clump either, and no two flecks sharing a row or column, since a lattice is exactly what the eye finds. A pin is a round ink head with a shaft, sitting over the card's top edge so it reads as holding the card on rather than printed on it.

**A card that would not drop — and what it cost to find out.** The board shipped on HTML5 drag-and-drop and cards would not drop: picked up, then snapped back. The first fix set `dataTransfer.setData`, which native drag-and-drop does require, and changed nothing. What kept the bug alive is that **nothing available here can drive native drag-and-drop**: jsdom has no `DragEvent`, and the browser preview's remote-debugging mouse input does not start one either — a real drag on a _binder_ row, which works in the app, moves nothing in the preview. So two fixes were checked against a harness that cannot fail, and both reported success against a view that did not work.

Cards drag on **pointer events** now, the mechanism the project windows already use (F-41 step 4). They are real input in the preview and in jsdom, which turns an unverifiable gesture into one that can be walked end to end. Doing that found three more faults in a row, none of which a unit test would have shown:

- Capture must be taken **when the drag starts, not on the press**. Capturing on `pointerdown` redirects the rest of the gesture to the card wrapper, and the card's own button then never receives `pointerup` or `click` — so a card could not be opened at all.
- The click-suppression flag must be **cleared on every press** rather than left for a click to consume. A drag ending over a different card fires its click on the nearest common ancestor — the board, not the button — so nothing consumes the flag and it swallows the next real click instead.
- A dropped position must be **held by the board**, not merely written to the file. Documents are read on demand and writing a position does not change `project`, so nothing re-read them and the card returned to its old slot the instant the drag ended — the snap-back once more, from the other end.

And one that only a real click in the browser could show: the CSS that made cards positioned landed on `.timeline-line-card` rather than `.scene-card`, because the anchor text I matched was not unique to the rule I meant. The cards stayed in flow, so every card drew in the wrong place while its inline position said otherwise, and the timeline quietly gained an overflow rule it never asked for.

**A test that was lying.** The binder-order tests used a fixture titled Alpha/Bravo/Charlie — already alphabetical, so sorting the cards by title was indistinguishable from binder order and the guard passed against code that ignored the binder entirely. The fixture is now deliberately out of alphabetical order, and the guard fails against both a title sort and a reversal.

### The Corkboard menu ✅ shipped — the outlining toolset in one place

Requested 2026-10-15, after the board landed. The five story-structure views and the board itself now live under a **Corkboard** menu of their own, between View and Project, with `⌥⌘B` switching between the board and the manuscript.

**Why they were hard to find.** The board sat in View; the timeline, plot graph, plotlines, character graph and world map sat in Project, beneath Writing Stats and above Backup and Sync Settings — filed as housekeeping, next to the things that move bytes around. Nothing in that arrangement said they are the _same scenes seen differently_: as cards, as a line, as a curve, as a cast, as a map. Grouping them is the first concrete step of the unification F-42 is after, and the board names the menu because it is the surface the rest belong to.

**`⌥⌘B` is a toggle, not an opener**, because the board and the manuscript are the two places a writer works and one key should move between them. From anywhere else — a folder listing, the stats page, a story-bible entry — it goes _to_ the board rather than doing nothing, since "not the board" is the only thing the other half of the toggle needs to know. The menu item renames itself to the place it would take you (Corkboard ↔ Manuscript) rather than naming where you already are. It uses `e.code`, not `e.key`: Option remaps the character on macOS (⌥B is "∫"), so a handler checking `'b'` would silently do nothing on the platform it was designed for — the trap `⌥⌘F` and `⌥⌘T` already carry comments about.

**Two places had to move with it**, and they are the ones that rot quietly:

- The **command palette's subtitles**, which name the menu an item lives under. They still said "Project". A subtitle is _searched_, not displayed, so this is not cosmetic: it is what makes typing "corkboard" turn up all five views, and left stale it would have sent a writer to a menu the items are no longer in.
- The **board's own pinned strip**, which offered three of the five. The strip and the menu are two statements of the same set, so Plotlines and Characters were added; if they disagree, neither tells a writer what the outlining tools are.

Tests cover the grouping, that nothing was left behind in Project (a half-done move is the likely failure), the toggle in both directions and from a third view, the palette search, and the strip — with the `e.code`/`e.key` trap and the half-done move both verified by injection.

**Card type, 25% larger** (requested 2026-10-15): title 12→15px, folder and foot 10→13px, excerpt 11→14px, in whole pixels because the chrome face is a pixel font. The **card stays 210x200** — it was grown to fit and then put back, because the card size is the thing a board is read by, so the opening gives up words instead: the excerpt is cut from 140 characters to 90, and the folder is one line with an ellipsis rather than three of a deep path. An excerpt is there to say which scene this is, not to be read.

Two layout faults came out of it, both of which put the word count _outside_ the card's border:

- `.scene-card-face` had `overflow: hidden` but **no bounded height**, so it was sized by its own content and simply overflowed the card's fixed height. The card is a flex column now and the face is `flex: 1; min-height: 0` — the `min-height` is the part that actually lets a flex child shrink below its content and clip.
- A title that wrapped to two lines then pushed the foot out anyway. The **excerpt** takes the leftover space (`flex: 1; min-height: 0`) while everything else in the face is its own height, so a long title costs the opening a line instead. Both were found by measuring the rendered boxes — the face was 250px inside a 240px card — rather than by looking at a screenshot.

### F-44 · Guided help ✅ shipped

Requested 2026-10-15. The **?** in the status bar (or `WyrmStar → Guided Help`) turns on a mode where hovering a control explains what it is for. Esc, or the same button, turns it off.

**Why a mode rather than tooltips everywhere.** A `title` attribute cannot be styled to match the app, appears whether or not it was wanted, and is impossible to review as a body of writing. A mode is also honest about what it is: a writer asking "what is all this?" is doing something different from writing, and the banner says so while it is on.

**The copy lives in one file** (`lib/help.ts`), and a control opts in with `data-help="<id>"`. What earns an entry is the vocabulary **WyrmStar made up** — the binder, checkpoints, the story bible, scene tags, the board, where a project lives — not Save and not Bold. Fifteen controls so far.

**Clicks on an explained control are swallowed while the mode is on.** Someone asking what a thing does has not asked to do it, and the marked controls include minimise, trash and the scene tag. The cost is that the mode must be left deliberately, which is also what stops it being a mode you fall into and cannot escape.

**Esc stops propagating.** It is already "back" and "close the dialog", so without that, leaving guided help would also walk the writer out of whatever they were reading about.

**Placement is a pure function** (`tipPosition`), for the same reason the window and board geometry are: jsdom has no layout engine. It flips the tip **above** a control when there is no room below — which the binder, being most of the window's height, did immediately — follows the pointer for a control too tall for its own bottom edge to mean anything, and clamps at both screen edges.

Both drift guards read the source: `tests/guided-help.test.tsx` fails if a marked control has no copy, or if copy exists for a control that no longer does. Verified by injection, as were the swallowed click and the Esc guard — the first version of the click test clicked the trash row, which only expands an empty list, and passed just as happily with the guard removed.

**Left for later:** the mode explains controls, not workflows. A first-run tour, or an explanation attached to a _view_ rather than a control ("what is this page for?"), would both fit the same machinery.

### F-45 · Characters and locations on the corkboard, Add Card, Stack ✅ shipped

Requested 2026-10-17 as the first of a run of corkboard features (the rest: string connections between cards, portraits on character and location cards). Three kinds of card now — scenes, characters, locations — all dragged, opened and stacked the same way; **Add Card** makes a new one or puts an existing entry on the board; **Stack** gathers the board into piles by kind and **Unstack** puts it back.

**Membership is deliberate, not automatic** — the one design question that was genuinely the writer's, settled with him. Scenes appear on the board automatically, as they always have. A character or location appears only when it is _put_ there: `entity.onBoard`, the World Map's "Place on Map" model rather than the scenes' one. The alternative — every entry in the story bible as a card, always — was simpler and busier, and would have left no way to take a card off short of deleting the entry behind it. A card comes off with the small × in its corner, and the entry stays in its book.

**Add Card asks what kind first**, because the answer decides what gets made: a scene is a new document in the manuscript, tagged and empty, exactly as F-42 settled an outlined scene should be; a character or location is a new story-bible entry, born with its card. For the two bible kinds the dialog also lists the entries that exist and are not yet on the board — "put Elara on the board" is at least as common as "invent someone new", and a second copy of a character is never what anyone meant. The scene is made by a new store action, `addSceneDoc`, which is `addDoc`'s primitives minus its last two lines: it does **not** select the document or start a rename, so the board stays up and no rename field is left dangling in a binder that is not mounted. It lands at the end of the Manuscript folder, found by title with a positional fallback, since nothing in the data model marks the manuscript root and the writer can rename or trash it.

**Stack is a way of looking, not an arrangement.** Three piles in kind order, each cascading by 24px so every title shows — the tableau in a game of patience, which is the look a writer reaches for when they say "stack them". Nothing is written while the board is stacked; Unstack returns every card to wherever it was, and Tidy unstacks too. The one exception is deliberate: a card dragged _out_ of its pile is a card the writer meant to move, so it is placed like any other drop and stays out until the board is unstacked.

**Entity positions needed main-process code that scene positions did not.** `DocMeta` passes through `parseDocFile`/`writeDoc` whole, which is why `boardX`/`boardY` on a scene lived entirely in the renderer. Entity frontmatter is read _field by field_ and written only when set, so `onBoard`/`boardX`/`boardY` had to be added to both `parseEntityFile` and `writeEntity` — with `!= null` for the positions, because 0 is a real coordinate and truthiness would drop a card at the board's left edge.

**The drag is tracked on the document now, not the card.** Found by the browser preview's drag tool, which delivers a single coarse move: the card received its `pointerdown` and nothing else, because the first `pointermove` landed wherever the pointer had jumped to, and only a move _received by the card_ could take capture. A fast flick on real hardware does the same thing and the writer sees a card that did not move. The gesture now attaches `pointermove`/`pointerup` listeners to the document on the press and removes them on the release, so where the first move lands is irrelevant; no capture is taken at all, which also keeps a plain click reaching the card's own button. The test that pinned the old rule ("capture only after the move") became one that dispatches the move and the release on the body, deliberately not on the card.

**A latent sync bug this would have made common**, found by the readers and fixed here: `mergeFrontmattered` merges per key over the union of both sides' keys, so an optional key _cleared_ on one device — which the writers do by omitting it — merged to `undefined`, and gray-matter throws on an undefined value. The sync then failed outright ("SYNC — NEEDS YOUR EYE") rather than merging. Tidy clears `boardX`/`boardY` from scenes today and from entities now, so this went from rare to routine. The merged frontmatter now drops any key whose value is undefined, with two sync-engine tests that failed against the unfixed code with the exact YAML exception.

**Left for later, deliberately.** Collections like map pins never got the structural frontmatter merge either (`isFrontmattered` matches only documents and the three bible folders), so a both-device edit of the same pin reaches the writer as a raw FILE conflict, contrary to what the `MapPin` comment claims; nothing in this PR changes that. Pulling a card out of a stack and dragging in general both write the entry's `modified`, as placing a scene writes the document's.

### F-46 · Red string between cards ✅ shipped

Requested 2026-10-17 with F-45. A **String** tool on the board: with it up, clicking a card pushes a pin in where it was clicked, and a second pin on a different card runs a red string between them. Esc pulls a waiting pin, or puts the tool down; clicking a pin while the tool is up pulls the string away. The strings follow their cards through drags, stacks and tidies.

**An end is anchored to a card, as an offset into it, never to a point on the cork.** A string between two cards has to survive either card being dragged, stacked or tidied, and a point on the board would be left behind by all three. `stringPoints` turns the anchors into board coordinates for the card positions _of the moment_, including a card mid-drag, which is what makes the string move with the card rather than catch up at the drop.

**Stored like map pins: one frontmatter file per string** (`strings/<id>.md`), so two devices adding different strings merge as unrelated files; as with map pins, a both-device edit of the _same_ string reaches the writer as a FILE conflict. Loaded by the board when it opens, not on project open — the pattern every project collection follows. `boardStrings` is in `SLICE_KEYS`, with a one-line test that is the only thing that would catch the omission.

**A string whose card has left the board is hidden, not deleted.** A character taken off the board can come back with Add Card, and a trashed scene can be restored; cascading the delete would turn a reversible action into one that quietly lost the writer's connections. Nothing cascades; the view skips a string it cannot draw.

**The string hangs.** A quadratic rather than a ruled line, with a sag that is a fraction of the span and capped (`STRING_SAG`, `STRING_MAX_SAG`), so neighbours are joined almost straight and a string across the board droops but never into the next row of cards. It hangs the same way whichever pin was placed first. Pure, so the droop is a number in a test rather than an impression in a screenshot.

**The one colour outside the palette's two inks.** `--string` is a red declared at `:root`, deliberately: red string between thumbtacks is the one thing everyone recognises a pinboard by, and an ink-coloured string would read as a ruled line. A palette may restate it (none of the sixteen do), and `tests/palette-fonts.test.ts` deliberately does not check it the way it checks `--cork` — that loop asserts a variable is drawn in the palette's ink, which this one must not be.

**Pins are inert unless the tool is up.** The string layer takes no pointer events, so a card under a string still drags; pin heads take clicks only while the tool is up, so a pin can be pulled without a pin being something you pull by accident. Pinning never opens the card: the face's click places the pin instead, and a drag that ends on a card is still not a click.

Esc in string mode stops propagating, for the reason guided help's does: Esc is also "back", and putting the tool down should not also walk the writer off the board.

### F-47 · Portraits on character and location cards ✅ shipped

Requested 2026-10-17, the last of the corkboard run. A character or location can carry a picture, chosen with the native file picker, kept inside the project beside its entry, and shown on the entry's card on the board and in its editor.

**The image is a data: URL over the bridge, not a file path.** The three transports were measured in a standalone Electron probe before building: `file://` loads in the packaged app but is refused under `npm run dev` by Chromium's local-resource rule for a non-file origin (not by CSP, so no CSP change could fix it); a custom `wyrm://` scheme works in both but needs a privileged-scheme registration before app-ready, a CSP edit, a traversal guard and a registry of open project roots that main does not keep; a data: URL needs **nothing** — the shipped CSP already carries `img-src 'self' data:` for the cork and dithers, and it works identically in dev, in the packaged app and in the browser-preview mock. The renderer names an entry's id and never a path, the same discipline `doc:read` and `entity:*` already keep.

**Stored beside the entry** as `characters/<id>.<ext>` or `world/<id>.<ext>` — `listEntities` already ignores anything that is not `.md` in those folders — so the image travels with the entry to a backup, to GitHub and to another machine. The frontmatter field is the project-relative filename. **Deleting an entry deletes its portrait** (found in review: nothing else would ever list or remove the image, so it would have sat in the folder, in every backup and on every synced device, for an entry that no longer existed).

**It could not ship with sync until the merge engine carried bytes.** The readers found it and an agent proved it: `completeMerge` built the merged tree through `TextDecoder` and `materialize` wrote it back as UTF-8, so a PNG that _neither device touched_ came out of the first divergent merge with every invalid byte replaced by U+FFFD — a 10-byte probe became 20 bytes — while the sync reported **merged** and pushed the corrupted copy. Fast-forward pulls, pushes, backups and clones were always byte-safe; only this path was not. Content the engine did not compose itself now travels as bytes (`blobAt`, a target of `string | Uint8Array`, `materialize` writing each as-is); the only strings left in the merged tree are the frontmatter merges the engine wrote. Three sync-engine tests put 512 bytes of deliberately invalid UTF-8 through a divergent merge in each direction and assert `Buffer.equals`; all three failed against the unfixed code. A text file with a BOM now survives a merge too, which the decoder used to strip silently.

**Grayscale on the card and in the editor**, deliberately: a colour photograph on a two-colour page reads as a sticker from another app; a grey one sits on the cork like a clipping. One CSS line to remove if a writer's own art is meant to be seen in colour.

**Noted while here, not fixed:** the oracle's always-clean merge driver returns _ours_ for every both-modified blob, including ones the detector's diff3 merged cleanly — so whenever some _other_ file conflicts, a non-overlapping both-sides edit to the same file (project.json edited in different places; a document where one device changed frontmatter and the other the body) is quietly reduced to this device's version. Both parents remain in history, so it is recoverable, but it is silent. Only reachable when a conflict exists at the same time. Logged as I-13 below.

### F-49 · Quit ✅ shipped

Requested 2026-10-27. **File → Quit (⌘Q)**: in File, where the early Mac kept it, and not gated on a project, so the Welcome screen quits too.

**Every way to quit now saves first.** Before this, ⌘Q, the WyrmStar menu's Quit and the Dock's Quit went straight to Electron. They relied on `beforeunload`, which starts the save and a checkpoint of the front project and waits for neither. On Windows and Linux the window's close box, the usual way out there, did the same. Now main holds every quit at `before-quit` (`main/wyrm/quitGate.ts`) and asks the window, which runs the same `quit` action as the menu item:

1. The page is saved while it is still on screen. If it cannot be saved, the writer is asked, and may stay.
2. The window shows only "Saving your work…". Everything else closes, and **every part saves the way it does when it closes**: a card's back, a name being typed on the map, a nudge waiting to settle. Nothing more can be typed.
3. Quitting waits for every one of those writes (`apiSettled`: each call to the bridge is tracked while it is in flight). A disk that stops answering is given ten seconds, then the writer is asked whether to quit anyway or stay.
4. Every open project with work since its last checkpoint is checkpointed, parked ones too. A checkpoint gets eight seconds: the files are saved by then, and a missed checkpoint loses nothing.
5. The app goes.

**It never traps the writer.** With no window open there is nothing to put away, and the quit goes at once. A window that does not answer within five seconds (hung, or with nothing listening) is quit anyway. Pressing ⌘Q twice quits once. On the Mac the close box closes the window and the app stays, as Mac apps do; that path still has only `beforeunload`.

**The projects stay open as far as the next launch is concerned**, as they always have on quit. Quit does not close them one by one, which would empty the reopen list.

**The adversarial review confirmed four findings, all fixed with tests and mutation-checked.** The first version saved only the page, so a card back left open, a map name being typed or a nudge still settling was lost: they save when they close, and a quit closed nothing. Text typed during the checkpoint wait was lost the same way. A save that never finished left the app unable to quit, with every later quit swallowed. And the close box on Windows and Linux skipped the save altogether.

**Why this belongs with the corkboard rather than beside it.** Everything already keys off scene documents. A scene is a document tagged `scene`, and `timelineOrder`, `timelineDate` and `tension` already live in its frontmatter; the timeline, plot graph and plotlines are all views over that one set. So the corkboard is not a new feature so much as the **missing view**, and outline mode is the thing that fills it without requiring prose first. Framed together, the existing tools stop being five separate dialogs and become one outlining toolset: the same scenes as index cards, marks on a timeline, points on a graph, pins on a map.

#### What is genuinely new

Two of the form's fields cross a line the app has not crossed before.

**Characters-in-scene is the first _stored_ link between a scene and the story bible.** Today that connection is entirely derived: `lib/entities.ts` matches names in prose and `lib/entityLinks.ts` renders decorations, never marks, never written to the file. The form needs the opposite — an explicit cast list with per-character attributes hanging off it. This is an addition to the model, not an extension of it, and it is what makes character plot views possible later: who appears where, wanting what.

**Scene→location is new too.** The map pins _locations_ (`MapPin` → a World Book entity); nothing records which scenes happen at one. Showing scenes on the map needs that link stated.

#### Settled

- **The form shows every field, and every field is optional.** Outlining is fast and loose — a six-field form plus per-character sub-forms is otherwise most of two minutes a scene, and the honest failure mode is that the writer stops outlining in the app. Fields are visible so they prompt, nothing blocks, Enter saves and opens the next.
- **Act is an attribute, not a container.** It records which act of the story a scene falls in — traditionally three. It does **not** organise the binder and is not binding on the timeline; its job is grouping on the plot graph, so the writer can see which acts are heavy with scenes and which need developing. The binder still organises; Act annotates, the same shape as `tension`. Stored as a free label with remembered suggestions rather than a fixed 1/2/3, so five-act and other structures are not shut out.
- **Scene Type is free text with remembered suggestions**, matching how tags already work. A closed vocabulary would style corkboard cards more reliably but imposes someone else's story vocabulary on the book, which is the wrong trade for this app.
- **Each palette defines its own cork and pins.** Cork is a dither, a pin is a few pixels of ink — declared per palette like the existing dithers and scrollbar arrows, so Green phosphor gets a phosphor corkboard and Manuscript a vellum one. One fixed cork-and-brass look would fight every palette and read as a foreign object in BIOS or Green. This keeps the two-colour discipline intact and stays inside machinery that already exists.
- **Outlined scenes are real documents from the moment they are added**, with empty bodies. Everything else — timeline, graph, map, corkboard — reads documents, so anything else would mean a second kind of scene and two code paths for every view.

#### Proposed shape

Scene frontmatter gains, all optional:

```yaml
act: 'II'
sceneType: 'confrontation'
location: <world entity id>
conflict: 'Reed wants the ledger; Maren will not open the shop.'
cast:
  - entityId: <character entity id>
    motivation: 'Owes money he cannot name'
    goal: 'Leave with the ledger'
    note: 'Lying about the fire from the first line'
```

`note` rather than a fixed third attribute: "mood" was floated but not settled, and a free line covers scene-specific traits without guessing at the right vocabulary. If a pattern emerges in use, promote it to its own field then.

#### Open

- **Build order.** The corkboard is already owed as the last Execution-order item, and it is the surface outline mode lives in. Building it first against today's scenes gives somewhere for the form to land and shows whether cards feel right before investing in the form.
- Whether "outline mode" is a distinct mode or simply what the corkboard _is_. The request describes clicking a scene to open the writing interface, which is what a corkboard does anyway.
- The map's own skeuomorphism — making a map look like a map — is noted as separate standalone work.

### F-43 · Bring a project down from its remote ✅ shipped

Create a local project by cloning one that already exists on GitHub, as a peer of New Project, Open Project and Restore from Backup.

Requested 2026-10-14, while setting a second computer up.

**The gap.** Sync connects an _existing local_ project to a remote; nothing brings one the other way. A writer with a novel synced from one machine has no way, inside the app, to get it onto a second — they have to copy the folder by hand or clone with `git` outside the app, which the brief's §10 decision deliberately does not require them to have. That is the whole point of GitHub sync ("pick up where you left off… falls out of this for free"), and the one direction that was never built.

**It is nearly all there already.** `github-auth.ts` already calls `/user/repos`, so listing the signed-in account's projects needs no new auth. `SyncTransport.fetchMainHead` already fetches a remote into a repo. And `restoreBackup(backupPath, destPath)` is the precedent for materialising a project into a fresh folder from an existing repository — the remote case is the same job with a different source. Cloning is init-remote-fetch-checkout rather than a `clone` call, because isomorphic-git is driven directly, the same way `backup.ts` hand-rolls its mirror.

**Built 2026-10-15.** `File → Bring Down from GitHub…`, and on the Welcome screen beside Restore from Backup — which is the case that matters most, since the moment you need this is the moment the machine has no project on it at all.

**All three questions settled the way the entry leaned:**

- **Both, list first.** The list is friendlier and needed no new permission (`createPrivateRepo` already used `/user/repos`), but it can only ever show the signed-in account's own spaces — the address field is what covers a novel shared by a collaborator, or an account this machine is not signed into. Failing to read the list is the _ordinary_ case here, not a failure, so it reports and leaves the field working rather than taking the dialog down.
- **Validated before opening, and it cleans up after itself.** A repository with no `project.json` is refused with "That GitHub copy does not contain a WyrmStar project", and **anything that fails after the folder is created takes the folder with it** — that refusal is the expected case, and a half-made project left behind would make the writer's next attempt fail on "already exists" for a folder they never made.
- **It arrives already connected**, `mode: 'github'` with its remote set, so it syncs immediately rather than dropping the writer into the sync picker to choose GitHub for a project that plainly came from GitHub.

**A third button broke the Welcome screen's button row** (reported from a screenshot). `.dialog-buttons` is justified to the right, so a row wider than its dialog overflows _backwards_ — "From GitHub…" hung off the **left** edge of the dialog rather than being clipped at the right where it would have been obvious. Fixed in two parts: the row now wraps, which makes spilling structurally impossible, and the Welcome dialog's `min-width` goes 460→600px so it does not need to in the default face. Button widths depend on the palette's chrome face, so no fixed width could be relied on alone — all sixteen palettes were measured in the browser, and none now overflow or wrap. The guard reads the rule from source, since jsdom has no layout engine.

**Hand-rolled init-remote-fetch-checkout**, not a `clone` call, because isomorphic-git is driven directly here the same way `backup.ts` hand-rolls its mirror — and because the fetch goes through the **injected `SyncTransport`**, which is the seam carrying auth in production and a bare repository on disk in the tests. So the init, the ref writing, the checkout and the project that comes out are all exercised for real; only the network is stood in for.

The test that matters most is the last one: after cloning, **the sync engine runs against the same remote and finds nothing to do**. That is the proof the clone is a peer rather than a lookalike — history and all — rather than a folder of files that would conflict with everything on its first sync.

**Today's workaround, and why it is not good enough:** clone by hand and use Open Project. It works, but the app sees `mode: 'unset'` with a `remoteUrl` present, so the writer is asked to choose a sync path for a project that already has one, then walked through connect-project to re-attach a remote that is already in `.git/config`.

- **The envelope cards have a drop shadow** to give them depth. It is the app's hard-offset shadow in ink, never a soft or faded one, so the drawer stays inside the 1-bit look.
- **Everything is drawn in the palette's ink and paper.** The folder is the paper with a light ink dither, not a brown, so the drawer works in every palette.

**Making a card read as a loose sheet** (decided 2026-10-28, from a mock-up):

- **A paper clip** holds the default card to the folder, drawn in pixels in ink. Where its wires run side by side, at least one pixel of paper separates them, and a one-pixel paper outline keeps the clip clear of the card's border. When another card is dragged to the top, the clip moves to it.
- **A slight tilt**: each card sits a little off straight.
- **Paper grain**: a sparse speckle of ink on the card.
- **No flap line.** A dotted envelope flap across each card was tried and dropped, because it didn't read as an envelope.
- **No pocket.** A pocket lip over the bottom of the stack was considered and dropped, because nothing the writer can click should be hidden.
- **Dragging a card**: it lifts, its offset shadow grows, and the clip moves to whichever card lands on top.

**Save points, not commits** (decided 2026-10-28). The GitHub side should not feel like a GitHub integration. Commit Checkpoint is coder's language, but a writer knows what an explicit save point is. So the command becomes **Create Save Point**, and ⌘S runs it. Tips or coaching in the app may come later, to introduce the patterns. The same rule applies to the GitHub tab's wording: say what happens to the writer's work, not which git operation runs.

**Removable drives** (decided 2026-10-28). Any drive other than the main one (C: on Windows, the startup disk on a Mac) is a fair guess for a removable drive. Adding a Disk location asks with a toggle whether the drive is removable, and the guess sets its starting position. Choosing removable shows a warning that a save skips the location whenever the drive is missing. The rest is up to the writer. This is how F-40 already treats a card that isn't plugged in: skipped, not failed.

**The project's own folder is a card** (decided 2026-10-28). On a computer the project lives in its own folder, and the app writes there as the writer types. That folder is the first card, **This computer**, so every project starts with one location. It can be moved down the list, but **never removed**. The three-location limit counts it.

### F-51 · Resolving conflicts, visually ✅ shipped

Split out of F-50 (2026-10-28), whose Conflicts tab opens today's resolution screen: one passage at a time, keep mine, keep theirs, or keep both as a variant.

**The idea** (Geoffrey, 2026-10-27): a skeuomorphic merge. Each side's changed text is broken into cards, and the writer drags the ones they want onto the page where they belong. A resolution the writer can see and touch, not a choice between two versions of a file.

**The screen** (agreed 2026-10-28, from a mock-up):

- **The page in the middle, Local on the left, Incoming on the right.** Each side is labelled with when it was written, such as "This computer · today 2:14 pm" and "Other computer · yesterday 9:40 pm". That is often the quickest way to remember which draft is the better one.
- **One disputed passage per page**, drawn as a manuscript page in the prose face: the text both computers agree on, with a few paragraphs either side for context. A chapter with three disputes is three pages.
- **A dashed gap marks where the disputed passage was.** It shows how the passage read before, crossed out, and is gone when the writer finishes.
- **One card per paragraph.** The merge already compares paragraph by paragraph (each paragraph is one line in the saved file), and writers think in paragraphs. Each side's paragraphs for a dispute are a stack, in order. Finer control may come later, if long use shows it is needed.
- **Underlines show what changed** in each card, against how it read before. Without them, two cards from the same paragraph are a game of spot-the-difference. A paragraph that had no before gets a **New** tag instead.
- **Dragging a card over the page shows a cursor where it will land.** The cursor lands only between paragraphs. Anything finer is fixed in the manuscript afterwards, by copy and paste.
- **Both cards can go in.** A card cannot go inside another card's text, for now.
- **A placed card stays a unit until the writer finishes**, marked Local or Incoming. It can be dragged again, or back to its stack.
- **The paper clip on a stack moves the whole stack, in order.** The mock-up left this unclear, so hovering the clip says what it does, the pointer becomes a hand, and guided help explains it. **All into the gap** does the same without dragging.
- **The page is not editable here.** This screen is for arranging; writing happens in the manuscript.
- **The bin** takes a card the writer doesn't want. It keeps the card until Finish, and can put it back. After that the text is still in the history, because the combined save point keeps both computers' versions.
- **The scratch pad** takes a card the writer can't bear to bin. It is never part of the book.
- **⌘Z** undoes every move on this screen.
- **Finish is never dead.** Cards left on the stacks go to the scratch pad, and the button says how many.
- **Later** leaves the screen and keeps the arrangement while the app is open.
- **It is a view in the novel's own window**, like the corkboard, not a dialog over the whole app, so the other open novels stay usable.

**Changes only one side made**, in a chapter that also has a dispute. Today the whole chapter comes to the writer, because two devices editing one document's prose never merges on its own. On this screen those changes are already on the page, marked "only changed there", and can be lifted off like any placed card.

**Edge cases:**

- **A paragraph deleted on one side and edited on the other:** that side's stack says "Deleted on your other computer", and leaving it empty agrees.
- **A whole chapter deleted on one side, the binder, an image:** these are not paragraphs. Each gets a simple page on the same screen, keep this one or that one, as today. Story-bible entries are prose and get cards, as chapters do.

**A Both edits card** (first version, if it can be done cleanly). The commonest real conflict is a typo fixed on one computer and a different sentence rewritten in the same paragraph on the other. When a dispute is one paragraph on each side and the two changed different words, so that a word-by-word three-way merge of the paragraph is clean, a third card offers both edits combined. It is only ever a card: nothing is combined unless the writer places it. When the changes overlap, it isn't offered.

**When the screen comes up** (changed 2026-10-28 from "whenever a conflict is found"):

- **Only when the writer asked for the sync**: Save Now, Sync Now, or Resolve… in the Conflicts tab. A background sync that finds conflicts marks the envelope and the Conflicts tab "!" and waits. A timer never pulls the writer off the page mid-sentence.
- **Only sending to GitHub waits for it.** Saving on this computer and copying to drives carry on, so a conflict never stops the book being backed up.

**The scratch pad** (agreed 2026-10-28). The name stays: it should feel tangible, like an index card full of lines or a little legal pad for leaving notes. Writers are reluctant to throw changes away, and this is where they go instead.

- **A pile of scraps, one file each** (`scratch/`), never one document. Two computers adding to one file would make the scratch pad the next conflict. Each scrap says where and when it came from.
- **In the binder, beside the Trash.** Opening it shows the scraps on a ruled pad, and their text can be selected and copied into the manuscript.
- **Never in the book.** It is left out of Compile, word counts, stats and the corkboard. It is **in search**, so a cut line can be found again.
- **Move to Scratch Pad**, a command in the editor for any selection. It takes the text out of the manuscript and onto the pad, so cutting a passage never means losing it. Many writers keep a file of cuts anyway; this is that file.

**Writing on the pad** (settled 2026-10-28, with step 1): yes. Every scrap can be written on where it sits, and **New Note** adds a blank sheet on top; a note left without a word in it is not kept. A pad that could not be written on would not be a legal pad.

**Under the hood.** Today the engine resolves a whole file one way: mine, theirs, or both. This needs a new answer: the arranged text of each chapter, plus the scraps, in the same combined save point. The screen must also finish against exactly the two versions it showed, so background sync pauses for that novel while the screen is open, and a resolve whose versions have moved underneath is refused with a fresh list rather than applied.

**Build steps** (agreed 2026-10-28, one PR each):

1. **The scratch pad** ✅.
   - **Storage.** Scraps are one file each in `scratch/` (`main/wyrm/scratch.ts`). Two computers that each keep a scrap merge without asking. A scrap rewritten on both is a prose conflict, named on the resolution screen as the scratch pad.
   - **Where it lives.** **Scratch Pad** sits in the binder above the Trash, with a count. It is also in the Project menu and the palette. It opens in place of the page as a detour, so Esc goes back to where the writer was.
   - **The sheets.** Each scrap is a ruled sheet, newest on top, gummed along the top in ink. Each says where it came from and when: "Cut from “The Ferry”", "A note", and, for step 4, "Kept from … as written on this computer" or "on your other computer".
   - **Writing and copying.** Every sheet is a small editor with the page's own prose kit (`lib/proseKit.ts`, which the page now shares), so copying from it keeps bold, italic and highlight. Typing is saved as it settles, and again as the sheet goes.
   - **Go to “…”** opens the chapter a scrap was cut from, while it is still in the binder.
   - **Edit's Undo, Redo, Bold, Italic and Highlight** act on the sheet being written in, as they act on the page; anywhere with nothing for them to act on they are off, not silently dead.
   - **Throw Away…** asks first, and makes a save point, so the text stays in the history.
   - **Edit → Move to Scratch Pad (⇧⌘X)** puts the selection on the pad, and only then takes it off the page, following any typing meanwhile. If the passage itself changed, or another document came forward during the write, the passage stays on the page as well: twice is recoverable, a wrong cut is not. Shift must really be held, so with Caps Lock on, ⌘X stays an ordinary cut. It acts only with the page itself in focus, so a selection hidden behind a tag or rename field is never moved, and a held key moves once.
   - **Never in the book.** Find in Project searches the pad. Compile, the word counts, stats and the corkboard never read it.
2. **Laying out the pages** ✅. Pure and DOM-free (`lib/mergePages.ts`), and tested without a screen, including 300 random pairs of edits checked for the module's promises.
   - **Lining up.** The three versions are lined up paragraph by paragraph (`threeWay`), counting only paragraphs with words in them.
     - Changes that overlap, or start at the same place, are one passage.
     - So are changes that meet end to start where both add text: two additions at one place have no order of their own, and taking both would double what both added.
     - Changes that meet without both adding (an edit beside an edit, a deletion beside anything) are separate.
     - Paragraphs one side changed next to each other are one change, so a dispute takes in a neighbouring paragraph that side also changed.
   - **Blank lines** belong to the paragraph after them and travel with it. A change to them is spacing, never a dispute and never a page: it is taken from whichever side made it, this computer's when both did.
   - **Pairing.** Within a changed passage, each new paragraph is paired with the old one it edits (`pairUp`, the most alike, in order). Paragraphs rewritten past recognition still pair with the one they replaced, in order, as a diff's replace does.
   - **What goes where.** What neither side changed, or both changed alike, is fixed text.
     - A change only one side made is placed already, a card per paragraph, marked "only changed there". Taking a card off brings back exactly the paragraph it replaced, once; an added paragraph's card brings nothing back.
     - A paragraph only one side deleted is a struck "removed there" line, which can be put back with its blank lines.
     - A passage both changed differently is a dispute: a gap, a stack for each side, the side that deleted it outright (if one did), and the Both edits card when it applies.
   - **Cards.** Each card is one paragraph, styled as the page styles it, and underlined against the paragraph it replaced.
     - The words that changed are underlined (spaces at their edges excepted), and so is a hard break put where a space was.
     - A paragraph with nothing from before is **New**, tagged instead of underlined.
     - One with the same words but different styling is **restyled**, and one that lost words (shortened, or split in two) is **cut**.
   - **Both edits.** Offered only for a dispute of one paragraph a side, when a word-by-word line-up of it is clean, the result is neither side's paragraph, and it reads back through the editor as exactly itself (a stray marker in a hand-edited file would not).
   - **Pages.** Every dispute is a page, with two paragraphs either side, stopping at another dispute's gap. A page's edges are always items that never move (text or a gap), so cards placed at its top or bottom stay on it. Every change only one side made that no dispute's page shows gets a **review** page, nearby ones sharing one, so no prose merges unseen. The same paragraph added in two different places is two changes, each shown.
   - **Composing.** `placeCards` (a card already on the page moves rather than copies), `liftCard`, `restoreRemoved` and `composeChapter` give back the stored text exactly as the editor writes it, blank lines included. Windows line endings read as the editor reads them, and a line of non-breaking spaces is the paragraph the editor keeps it as.
3. **The engine's new answer** ✅.
   - **What a conflict carries.** A list of conflicts names the two versions it was made from (`heads`). Each conflict carries its text from before either computer changed it (`baseBody`) and when each side last changed it (`localAt`, `remoteAt`), so the screen can say "This computer · today 2:14 pm". The time is when the words themselves were saved there, looking through any merge that only carried them along.
   - **Arranged text.** Resolving takes a `ConflictAnswer`: a choice for every conflicted file, the versions it was made against, and the scraps to keep.
     - The new choice, **arranged**, is the merge screen's: the prose as the writer put it together. It is accepted for a document, story-bible entry or scrap that both sides still have, as text.
     - Its details (title, tags, synopsis, positions) merge field by field, exactly as a clean sync merges them; only the prose is the writer's.
     - Scraps are written in the same combined save point, and never over a file either side already has, even one whose name differs only in capitals; a scrap name the disk would refuse is refused before anything is written.
   - **Only against the versions shown.** The answer is refused with a fresh list, changing nothing, when the other side has moved, when this side's copy of a chosen file has changed since (typing after Later), or when a conflict is left without a choice. Work saved meanwhile in other files doesn't matter. The answer is checked field by field as it arrives from the page.
   - **No sync while the screen is up.** A sync asked for or made automatically answers with the list already on screen, without the network, and a project in a background window with its screen up doesn't sync on its own save points either. A sync that was already on its way when the screen came up leaves the list on screen alone when it lands. The store keeps the versions with the list, sends them with the answer, records the outcome on the novel that answered, and puts a fresh list on screen in place of the old one. Today's resolution dialog says why when that happens.
4. **The screen** ✅. It replaces the old resolution dialog, which is gone.
   - **Where it is.** When a sync the writer asked for finds conflicts, the merge screen covers the novel's window, so the other open novels stay usable. What it covers is left exactly as it was underneath, out of reach: the page keeps its editor, so a merge that lands reaches it, and an entry half-edited keeps its unsaved changes. The top bar says **Combine**, with ‹ Page n of m › between the pages.
   - **What it shows.** Each chapter both computers changed (a document, story-bible entry or scrap both still have) is laid out by step 2's pages. Local's cards stack on the left and Incoming's on the right, each headed "This computer · today 2:14 pm" or "Other computer · …". A side that deleted the passage says so ("Leave this side empty to agree"); a stack that has given every card away says "Nothing left here". The Both edits card, when there is one, sits under the page, and its place stays there while it is placed, so it can be dragged back.
   - **Cards** keep the page's bold, italic and highlight, underline the words that changed, show a changed hard break as ↵, and are tagged New, Restyled or Cut (Cut means words only taken out). A placed card is marked Local, Incoming or Both edits; one placed already is "only changed there".
   - **Dragging.** A card dragged over the page shows a cursor between the paragraphs nearest the pointer, and lands there. A press only becomes a drag after a few pixels, so a click is never a move. Only the part of the page that can be seen takes a drop, and scrolling mid-drag moves the cursor with the page. Dropping a card back where it was is not a move. The paper clip on a stack of more than one card moves the whole stack, in order, and says so on hover; **All into the gap** does the same without dragging. A placed card can be dragged again, back to a stack (the one on the page in front, where a card shows on two pages), to the bin or to the scratch pad. **All into the gap** puts the stack before any change to the next paragraph, never after it.
   - **Bin and scratch pad.** Both sit in the foot of the screen with a count, take dropped cards, and open a tray listing what they hold, each with **Put back**. A struck "removed there" line can be put back too.
   - **⌘Z** undoes every move on the screen. Undo in the foot does the same, and is off when there is nothing to undo.
   - **What isn't prose** (the binder, an image, a chapter one side deleted) is a page with a choice: keep this computer's, take the other's, or, where it can be, keep this computer's and the other as a variant.
   - **Finish** first asks for every choice still unmade, going to that page and saying so. Then it sends each chapter as arranged, and every card on the scratch pad or still on a stack as a scrap saying where it came from ("Kept from “The Ferry” as written on this computer"). While cards are left, it says how many go to the scratch pad. While it is on its way nothing on the screen moves, so what is sent is what the screen shows; an answer that comes back after the writer has gone to another novel is said when the screen next comes up.
   - **Later, or Esc,** sets the screen aside and keeps the arrangement while the app is open. An open menu or guided help takes its own Esc first, and Esc with a card in hand puts the card back. Resolve… brings it back, with every chapter that hasn't changed since as the writer left it.
   - **A fresh list** (the work changed under Finish) is laid out again in place, keeping every chapter that hasn't changed, and says why. A failed Finish says why beside the buttons and keeps the arrangement.
   - The arrangement and every move on it are pure (`lib/mergeScreen.ts`); the screen draws them and turns drags into moves.
5. **The keyboard and guided help** ✅.
   - **Getting round.** Tab goes between the stacks and the page, one stop each, coming back to the card last left there; ↑ and ↓ go between the cards in one. A stack of more than one card has its clip above its top card, so ↑ from the top card reaches it.
   - **Picking up and placing.** Return (or Space) picks up the card, or from the clip the whole stack, and a cursor shows on the page where it would go: where the card is, for one already on the page, so Return at once is no move; where it was taken from, for a change only one side made; or just after the gap, as All into the gap puts it. ↑ and ↓ move the cursor between the paragraphs, passing over the card's own place in one press, and Return puts the cards there. The card in hand is raised from its place, words still showing.
   - **Putting down.** Esc puts what is in hand back and keeps the screen up; ⌘Z waits while anything is in hand. Tab, a click elsewhere, turning the page or a press of the pointer puts it down too; switching to another program does not.
   - **Bin and pad.** Delete (or the Mac's delete) bins the card in focus or in hand, and S keeps it on the scratch pad, from a stack or the page; from the clip, the whole stack goes.
   - **Focus is never left nowhere.** It follows a card onto the page, and a card ⌘Z moves; after a bin it goes on to the next card, or to the stack or page itself once it is empty. A button that goes with what it moved (Into the gap, Put back) hands focus on, a tray's Put back only once the key is up. Finish takes focus back when its answer leaves it nowhere, and the screen gives focus back to where the writer was as it goes.
   - **The hint line** says what the keys do for a card, for the clip, and with cards in hand.
   - **Guided help** covers every control on the screen, the clip first; a test fails if a button or card falls back to the screen's own explanation. The ⌘/ legend has a Combining changes group.
   - **Tidied in passing.** A clipped stack's heading has room for the clip when it wraps onto two lines.
   - **Fixes from the adversarial review** (8 confirmed, 6 distinct):
     - A held Return no longer picks a card up, puts it down and picks it up again; only the arrows repeat, and a held Delete or S takes one card.
     - A click on a card gives it focus, so the keys act on the card the writer last touched, not one focused before; a card dragged and dropped keeps focus as it does from the keys.
     - Focus stays on the screen when ⌘Z takes away the button that had it (a tray's Put back, Into the gap), and when Undo, ‹ or › turns itself off; a focus moved once the key is up is never taken back from where the writer has put it meanwhile.
     - The cursor stays in sight when ↑ scrolls the page up.
     - Guided help says the Both edits card is both computers' edits, not one computer's paragraph.
     - The test that Finish takes focus back now fails without the code it tests.

## How we track work

- **This file is the plan.** Update it in the same PR as the work it describes — status changes, new backlog items, new known issues.
- **Backlog IDs are permanent** (`F-01`, `I-02`). Reference them in commit messages and PR titles so history stays greppable.
- **Bugs get logged here with their root cause**, not just a symptom, and are only marked fixed when there's a test or a verified reproduction behind the fix.
- **Feature requests land in the backlog immediately**, even half-formed — 💭 means "needs design before it can be scheduled," which is a real status, not a parking lot.
- **Execution order beats phase numbering.** The phase table describes scope; the Execution order section says what to build next and why. Re-sequence it deliberately, with the reason written down, rather than letting the brief's numbering decide by default.
- **Verify a merge actually landed** on `develop` before starting the next item (`git merge-base --is-ancestor <commit> origin/develop`). Two batches of work have silently missed the mainline — see the workflow rules in `CLAUDE.md`.
- **Start a fresh session per work item.** Long sessions re-send their whole history every turn; this file plus `CLAUDE.md` exist so a new agent can pick up full context in two reads instead.
